Part II

Foundations: what to learn before you build

TrustLoop touches three ecosystems and one discipline that beginners usually skip: measurement. You do not need to master all of it. You need enough of each to build the smallest honest version, and the judgement to know when a result is not trustworthy.

Foundation gate

  • I can write a typed extraction function and test it against saved markup.
  • I can train, persist, and reload a scikit-learn text pipeline.
  • I can explain AUROC, calibration, and why a score is not a prevalence.

Part IIII

Build: six phases from frozen contract to deployed demo

The order is deliberate. Prove the page is extractable, freeze the contract, build the scoring path, then the public boundary, then the interface. Authentication comes last because it is an access feature, not a prerequisite for scoring.

0.4
Dataset, codebook, and the acceptance gate
2–4 days · close decisions D22–D24

The project's honesty depends on this phase. Choose licensed data, write the annotation codebook, define the held-out sample, and freeze the numeric gate before training. Deciding the pass mark after seeing the result is how projects become unfalsifiable.

Tasks
  • Confirm licences for the training corpus and record them in dataset-manifest.json.
  • Write the codebook: organic, manipulated, and uncertain with explicit exclusions.
  • Plan the held-out manual sample: 200–300 EN and 150–200 FR reviews, sampling method documented.
  • Two annotators, Cohen's kappa target of at least 0.60, adjudication pass for disagreements.
  • Freeze the EN and FR gate table (Appendix F references the model plan).
  • Record D22, D23, D24 outcomes in the decision register.
RuleNo live TrustLoop review text is ever used for training. Inference text is processed transiently and never retained.
Proof of done

A signed-off codebook, a dataset manifest with hashes and licences, a gate table, a sample plan, and three closed decisions.

Phase 1 · 5–6 weeks

The analysis core, no accounts

The full path from a supported page to an honest score and explanation. No login, no database, no dashboard. One adapter, one model, one contract, and every failure state visible.

1.1
Data pipeline and annotation
4–6 days · the model is only as good as the labels

Build the dataset as a reproducible pipeline, not a folder of CSVs. Normalization, deduplication, source-aware splits, and a manifest with hashes make every later metric reproducible and every licence auditable.

Tasks
  • Normalize text consistently: Unicode normalization, whitespace collapse, no stemming that destroys the patterns you want to detect.
  • Remove near-duplicates across splits with MinHash or cosine similarity before training.
  • Split by product/page and by source into train, dev, calibration, and test.
  • Keep the calibration split untouched by hyperparameter tuning.
  • Write dataset-manifest.json: sources, licences, hashes, split counts, random seeds.
  • Add a script that rebuilds the splits from raw data and fails if hashes do not match.
Leakage checkIf a near-duplicate appears in both train and test, your AUROC is fiction. Run the duplicate check as a test, not a one-off notebook cell.
Proof of done

One command rebuilds the splits; the manifest matches the hashes; a leakage test fails when a duplicate is injected.

1.2
The baseline model
5–7 days · TF-IDF plus logistic regression, tuned on dev only

Word 1–2 grams plus character 3–5 grams, balanced class weights, regularisation tuned on dev. The linear form is chosen because its coefficients give an exact attribution, which is what makes the explanation pane truthful.

# the shape of the pipeline - one artifact, one decision path text_clf = Pipeline([ ("features", FeatureUnion([ ("word", TfidfVectorizer(ngram_range=(1,2), sublinear_tf=True)), ("char", TfidfVectorizer(analyzer="char_wb", ngram_range=(3,5))), ])), ("clf", LogisticRegression(class_weight="balanced", max_iter=2000)), ])
Decide in this step
Per-language vs multilingual (D24) Regularisation strength Minimum token frequency Language detector
Baseline before ambitionA transformer is an optional Phase 3 candidate, not a Phase 1 requirement. It may replace the baseline only if it beats it on the manual in-domain sample, passes calibration, and keeps top-5 explanation stability above 0.80.
Proof of done

A trained pipeline, a dev-only tuning note, and a one-line record of the per-language model decision.

1.3
Calibration and explanation
4–6 days · from raw score to a number you can defend

Calibration turns a model output into p_organic. Explanation turns the linear coefficients into at most five named signals with direction. Both have stability requirements, and both are tested against fixed inputs.

Tasks
  • Fit Platt scaling or isotonic regression on the dedicated calibration split; choose by dev reliability.
  • Report ECE, Brier, and a reliability curve per language.
  • Aggregate token contributions into the seven named signals; normalise across the full feature set.
  • Return the top five only, preserving original values and direction; do not renormalise the subset.
  • Show a numeric contribution only when the stability check passes; otherwise return the signal qualitatively.
  • Hash the full result and assert determinism for identical input and version.
# score mapping - no separate layer, no post-hoc band adjustment p_organic = calibrator.predict_proba(X)[:, 1] trustScore = clip(round_half_up(100 * p_organic), 0, 100) verdict = band_for(trustScore) # six fixed bands, boundaries frozen
Proof of done

A calibration report with ECE and Brier, a deterministic explanation function, and a top-5 Jaccard score across three runs.

1.7
Scoring client and failure semantics
3–4 days · failures are a feature, not an accident

A timeout must not become a low score. The scoring call is atomic for the batch: one timeout, malformed body, non-2xx response, or version mismatch marks every review UNKNOWN with the right reason. The extension then offers a manual retry.

// one attempt, atomic batch try: response = client.post(SCORING_URL, json=batch, timeout=3000, headers={ "X-Internal-Token": token, "X-Request-Id": requestId, }) validate_against_contract(response) validate_expected_model_version(response) return response except Timeout: return unknown_all(batch, "SCORING_TIMEOUT") except (ConnectionError, ContractError, VersionMismatch): return unknown_all(batch, "SCORING_UNAVAILABLE")
No silent fallbackDo not substitute a heuristic when the model is down. SIGNALS_ONLY is the only approved fallback, it has no score, and it is chosen per language and per adapter before runtime - not guessed at request time.
Proof of done

Tests simulate timeout, connection refused, malformed JSON, wrong model version, and 500; each yields the correct unknown state for every review.

1.8
Extension shell and the first adapter
5–7 days · the product becomes visible

The adapter owns selectors, eligibility, and page-specific rules. It extracts only eligible review text, keys each review with a session-scoped salted hash, batches up to ten, and never computes a score.

Build order
  • Manifest, service worker, content script, popup, and storage wrapper.
  • Adapter manifest: ID, supported-page description, selectors, fixture paths.
  • Eligibility: rendered, not hidden, non-zero box, not aria-hidden, extractable text.
  • Session dedup: adapter card ID when stable, otherwise salted normalized-text hash; memory only.
  • MutationObserver with 750 ms debounce and a 2 s minimum rescan interval.
  • Batch up to ten unscored eligible reviews into one analyze request.
// batching and dedup - the loop that must not spam the API onMutation → debounce(750ms) → scan() eligible = cards.filter(isEligible) fresh = eligible.filter(c => !seen.has(keyFor(c))) batch = fresh.slice(0, 10) send(batch) → seen.add(...) → render(results)
Proof of done

On a saved fixture, the adapter extracts the expected reviews once, survives DOM churn without resubmitting, and produces an explicit UNSUPPORTED_PAGE on an unsupported fixture.

1.10
Local history and storage privacy
2–3 days · off by default, metadata only

History is a convenience feature with a privacy cost, so it is opt-in and minimal. It stores timestamps, hostname, adapter, status, score, verdict, evidence, engine, model version, and reason code. It never stores review text, keys, URLs, or a persistent fingerprint.

// allowed history record - nothing else may be added without a privacy review { "timestamp": "2026-11-04T10:22:00Z", "hostname": "www.amazon.fr", "adapterId": "amazon.reviews.v1", "status": "SCORED", "trustScore": 73, "verdict": "LIKELY_ORGANIC", "evidenceQuality": "ADEQUATE", "engine": "MODEL", "modelVersion": "tl-text-1.0.0" }
Proof of done

Tests prove history is off by default, capped at 100 entries or 30 days, clearable, and contains no text, key, full URL, or fingerprint.

Adapter discipline
3–5 days · breadth only with proof

A second adapter is allowed only if it brings a manifest, a supported-page description, fixtures, and an explicit unsupported state. A generic fallback scraper is forbidden: it would turn "we could not find a review" into "we analyzed the page", which is a false claim.

Each adapter ships with

Proof of done

Every bundled adapter passes its fixtures and returns an explicit miss on a deliberately wrong page.

2.2
Local inspection surface
3–4 days · dev-admin only

You need to inspect bundled adapters, view fixtures and supported pages, toggle adapters locally, and read in-memory metrics during development. That surface is a local tool, not a product feature, and it must be impossible to reach by accident.

Scope

  • Inspect fixtures and the unsupported state for each adapter.
  • Local enable/disable toggles held in memory; no file writes.

  • No persistence, no accounts, no runtime adapter authoring.
Proof of done

The surface works locally, writes nothing to disk, and is documented as a development-only tool.

2.3
Profile isolation and the boot guard
2 days · "local-only" enforced, not promised

The default profile returns 404 for every admin path. The dev-admin profile binds to 127.0.0.1 and refuses to start if the bind address is not loopback. A verbal promise is not a security control; a boot failure is.

Proof of done

2.4
Content-free operational metrics
2 days · observe without collecting

You need to know whether the system is healthy without learning anything about the reviews. Counters by status, reason code, engine, model version, and latency are enough; anything per-review is a privacy incident waiting to happen.

Proof of done

What TrustLoop will not claim

These are not limitations to apologise for. They are the boundary that makes every other claim credible.

Not proof that a review is fake Not a bot or spam-account detector Not reviewer identification Not purchase verification Not a product-quality score Not a page or product aggregate Not a real-world prevalence estimate Not a generic page scraper Not an external AI provider Not a silent heuristic fallback Not a claim that French is supported without its gate Not a truth verdict

Critical success checklist

Revisit every two weeks. If more than two answers are "no", stop building and fix the foundation.

  • Is the contract still frozen? Any local edit to a shape is a version change, not a shortcut.
  • Does every unknown state have a reason code? No number, no verdict, no placeholder.
  • Is the model gated per language? English passing does not make French supported.
  • Can I reproduce the demo from a fresh clone? If not, the README is lying.
  • Is there review text anywhere it should not be? Logs, history, database, screenshots.
  • Are the tests still green? A skipped test is a decision to ship a known unknown.
  • Is the admin surface still local? Loopback bind, 404 by default.
  • Does the UI use the copy deck? Both languages, same claim strength.
  • Is the score explained without causation? Signals contributed; they do not prove.
  • Is the evidence folder current? A gate without a document is a rumour.
  • Did I take a rest day? Burnout is R-09 wearing a different mask.
  • Would I still defend this score under questioning? If not, fix the claim before the demo.

Final advice

Six things that will decide whether this project is impressive or merely finished.

01

Freeze before you build.

The contract, the gate, and the copy deck are cheaper to argue about now than to reconcile across three languages later.

02

Prove the page first.

If the adapter cannot extract five honest reviews from three variants, no amount of model work will save the demo. Run the spike before falling in love with the architecture.

03

Keep the baseline.

A calibrated linear model with stable attributions is more defensible than a transformer you cannot explain. Upgrade only when the evidence beats it.

04

Make unknown a first-class result.

The most credible moment in the demo is the system refusing to score. Design that state with the same care as the badge.

05

Write the evidence as you go.

Every gate produces a document. By Phase 3 the report is assembled; by the defense it is just reading.

06

Cut breadth, never honesty.

One site, one model, one contract, fully demonstrated, beats six half-adapters and a score nobody can justify.
