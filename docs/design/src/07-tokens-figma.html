SECTION 12Design tokens

Tokens are the contract between the charter and the code. A component uses a named value, never a hex code; a theme changes the values, never the component.

12.1 One source, three artefacts

tokens.css

The runtime source for the extension and options page. Custom properties only. No component classes, no resets, no app code.

tokens.json

The tooling copy for Figma variables, documentation, and any future generator. Same values, same names.

Figma variables

Two modes, Light and Night. Names mirror the token paths. A designer never types a hex value into a layer.

In v1 the three artefacts are updated together by hand; there is no build step that generates one from another. That is a deliberate trade: fewer moving parts, but the release checklist includes a value diff between tokens.css and tokens.json. When the project has a build pipeline, the JSON becomes the source and the CSS is generated.

12.6 Token rules

  • No raw values in components. A hex code, px padding, or duration outside this file is a defect. The review greps for # and px in component styles.
  • No gradients. There is no gradient token because no product surface uses one. A gradient in a mockup is a mistake, not a theme.
  • No colour-only states. A token cannot add a cue that the markup does not carry. The band ladder, arrow, label, and em dash exist in the component, not in the palette.
  • Night is explicit. The theme follows the extension setting or the OS preference, never the host page. It is applied with data-tl-theme="night", not by inverting values.
  • One new token needs a decision. Add the value to both files, update this section, and record it in D20. Do not sneak a one-off value into a component.
  • Values are versioned. A colour change is a charter revision, not a tweak. The PDF, the CSS, the JSON, and the Figma variables carry the same version.
The 4 px trap

Ten, fourteen, eighteen, and twenty-two are not spacing tokens. The 14 px mockup padding from an early draft was corrected to the 16 px gutter; the only off-scale offset is the 3 px hard shadow, which is a print device, not spacing.

The marker in Figma

Figma cannot bind a layer position to an arbitrary 0–100 score. Build three representative frames (for example 34, 51, 73) and annotate the formula left = score%. Do not create 101 variants. Production uses CSS, not the Figma frame.

13.4 Auto layout and constraints

  • Panel: vertical auto layout; width fixed at 360; header and footer hug; list fill. No absolute layers except the marker inside the track.
  • Row: horizontal auto layout; index fixed 22, score fixed 40, band fill, chevron fixed 12; gap 8; padding 10/16; min-height 58.
  • Chip: horizontal, hug contents, min-height 26, padding 3/7; the ladder is a nested component with six ticks.
  • Measure: vertical; score and band on one baseline; track fixed 7; scale labels 7.5; qualifier hug.
  • Text: no fixed-height text frames. Use auto height and “hug contents”; test the French string, not the English placeholder.
  • Constraints: header/footer pin to top/bottom; list fills; no stretch that distorts the chip or the mark.

13.6 Figma QA

  • Variables only. No detached colour or text style; switching Light/Night changes the whole frame.
  • No gradients or blurs. The only shadow is the 3 px hard offset. No glass, no glow.
  • Copy deck only. Every string is traceable to Appendix A; proposed strings are marked in the frame notes.
  • French first. The longest strings are set in French, at 320 px, before the English frame is approved.
  • States, not just the happy path. Every component has unknown, low, error, and focus where relevant.
  • No stock imagery, avatars, emoji, or AI-generated art. The mark and icons are the only graphics.
  • No detached instances. Overrides are limited to text and variant properties; geometry stays in the component.
  • 200% check in the browser. Figma zoom is not layout zoom; the real test is the built panel at 200% and 320 px.

13.7 The Figma prompt

The paste-ready brief lives in docs/design/figma-prompt.md. It contains the file name, the page structure, the variable collections, the component list, the exact palette and type, and the refusals. It is written to be pasted into a Figma AI or handed to a designer, and it repeats the anti-AI constraints because that is where generic output enters: violet gradients, glass cards, centred hero layouts, rounded pills, and decorative emoji.

14.2 Source hierarchy

  1. Product decisions and model plan. Score meaning, bands, copy deck, signals, evidence, privacy, D23.
  2. This charter. Visual and interaction rules, components, states, tokens.
  3. tokens.css / tokens.json. The values in code. If they disagree with the charter PDF, the PDF is stale; fix the PDF and the files together.
  4. Figma. The working file. It follows the tokens and the copy deck; it is never the authority for either.
  5. Screenshots. Illustrations, not specifications. Never hand off a screenshot alone.

14.3 What developers receive

Values

tokens.css and tokens.json. No hex codes in tickets. Import the variables once, then use semantic aliases.

Behaviour

Section 08's state matrix and Section 06's measure rules. Unknown, LOW, signals-only, loading, and error are part of the component, not follow-up work.

Copy

Appendix A. Normative strings are quoted; proposed strings are marked and need deck approval. No string is invented in code.

14.5 Change control

A visual change is a charter revision when it alters colour, type, spacing, a component's anatomy, a state, or a token. Update the HTML source, regenerate the PDF, bump the version and export date, update tokens.css and tokens.json, and record the change in the D20 row of the decision register. Band boundaries, band names, score meaning, and the copy deck cannot be changed here; they belong to product decisions and the model plan.

Versioning

Charter v1.0 is the baseline for the MVP and the defense. Minor revisions use v1.1; a new visual direction uses v2.0. The PDF file name carries the version. The Figma file carries a cover frame with the same version and date.

14.6 What not to hand off

  • Unmarked explorations. If an alternative was rejected, archive it with a date; do not leave it in the component page.
  • Detached instances. They drift within a week and cannot inherit the night mode.
  • Screenshots with sample review text. Keep the mockups free of realistic personal data; the host-page simulation uses obvious placeholders.
  • Untranslated strings. A French frame with an English label is not a French frame.
  • Gradient or glass variants. They contradict the charter; do not ship them as “options”.
  • A page-level number. No mockup, slide, or report figure may average reviews into a page score.
