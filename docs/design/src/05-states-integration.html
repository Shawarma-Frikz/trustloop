SECTION 08States and integration

The honest cases are the design. A missing estimate, a short review, an unreachable service, and a page with no reviews are not edge cases to be hidden; they are the moments when the product either keeps its promise or breaks it.

8.1 A failure is a sentence

Every failed or absent estimate resolves to one of three shapes: a sentence, a reason, and — only where it can help — one action. No infinite spinner, no red panel, no alarm icon, no “Oops”, no mascot, no apology paragraph.

The tone is procedural. The page is not broken; the estimate is absent. Say which, say why, and stop. A failure never borrows the visual language of a verdict: no band colour, no measure, no score cell.

Never

  • Show 0 for an unknown value.
  • Show a spinner after the request has failed.
  • Show a raw reason code in the interface.
  • Offer “Retry” for a page that will never be supported.
  • Keep a chip that no longer matches the page.

Geometry

Skeletons use the final row heights and column positions. Nothing moves when the result arrives except the content itself.

Motion

A 1.4 s opacity pulse between 100% and 72%, on skeleton bars only. Disabled under prefers-reduced-motion. No shimmer sweep.

Announcement

The page bar is a polite live region: “Reading reviews…”, then “3 reviews found”. Focus never moves on completion.

Rescan is not a first scan. The list stays readable, the chips stay visible, and the page bar says “Rescanning…”. On success the rows crossfade for 120 ms. On failure the rows stay and a single inline notice appears above them: “Couldn't refresh. Showing the last result.” with a “Retry” action. Navigating to another page clears the list and every chip at once; stale results are never carried across pages.

An empty block is left-aligned, uses the interface sans for the body, and puts the serif on the title only. It has no illustration and no icon. The error block uses the same shape; only the copy and the action change. A reason is always a full sentence, and the action is always a verb.

Codes are not copy

Reason codes belong in the API, logs, and support documentation. If a code is ever needed in the interface, it goes behind a collapsed “Details” row in options, never in the panel headline, and never next to a score. No code, review text, URL, or review key appears in logs or history.

8.7 Chip rules

  • One chip per review. No page-level chip, no product-level chip, no aggregate anywhere on the host page.
  • Top-right, 8 px inside the card's padding box. It must not cover the rating, the reviewer's actions, or the first line of text.
  • Collision fallback. If there is no safe corner, place the chip after the review body, aligned left, on its own line. It never overlaps.
  • Click opens the panel at that review. The chip is a button with an accessible name; it is not a hover tooltip and not a link to a third party.
  • The chip keeps its paper surface on dark host pages. It is an annotation, not a themed component. The 1 px outline keeps the edge visible.
  • No chip before a result. On first scan there is no placeholder chip. During an explicit rescan the last chip stays; on navigation it is removed.
  • Shadow DOM. Host CSS does not enter, extension CSS does not leak. No !important overrides of the host page.
  • Zoom and reflow. At 200% the chip wraps with the review header; it never covers text. The 44 px target scales with the page.

Screen reader order

The chip announces score, band, band position, and evidence before it announces “button”. Opening it moves focus to the matching review row and announces the band. A rescan announces the new count politely; it never steals focus from the host page.
