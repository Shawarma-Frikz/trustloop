CHAPTER 08 · PHASE 4Accounts, ownership, and persistence

Authentication is deliberately last because it is an access feature, not a prerequisite for scoring. When it arrives, it brings the first database and the first durable user data. The rule that protects the project is simple: accounts may own metadata about a scan, but never the review text, the review key, or a persistent fingerprint.

Phase exit condition

The access matrix is verified by tests. Admin functions require an authenticated admin role. History ownership and retention are enforced. No raw review text is stored. Migrations reproduce from an empty database. Tokens, passwords, and deletion behave as documented.

8.1 Decide the scope before writing a schema

Do not start with tables. Start with the answers a schema must encode. Write them into a decision row and into the phase evidence; a schema without a retention rule is a liability.

DecisionRecommended starting point
What history storesMetadata only: timestamp, hostname, adapter ID, status, score/verdict when scored, evidence quality, engine, model version, reason code. Never text, key, URL, or fingerprint.
Who owns a history rowExactly one user. Every read, delete, and export filters by the authenticated user ID.
RetentionDefine a maximum (for example 180 days) and enforce a scheduled purge. The user can clear earlier. Local history remains 30 days/100 entries.
Account deletionDeletes the user, refresh tokens, history, and audit references according to the audit policy; requires re-authentication.
RolesUSER and ADMIN. No self-service role elevation.
Admin protectionEvery /api/v1/admin/** route requires ADMIN. The local dev-admin profile remains a separate, loopback-only development tool.
Email verificationOptional. If not implemented, state the limitation and do not claim verified accounts. Password reset requires an email channel; if absent, omit it rather than faking it.
Token modelShort-lived access token (for example 15 minutes) plus a rotating refresh token (for example 30 days). Passwords hashed with Argon2id or BCrypt cost ≥ 12.
Contract impactNew endpoints and auth error codes are a contract event. Do not add them silently to the frozen analysis schemas.
Do not retrofit text storage

“Save the review so history is useful” is the shortcut that turns a privacy-preserving design into a content database. History is useful without text: the user can still see when a scan happened, what status it returned, and what the score was. If a future feature needs text, it needs a new decision, consent, retention, and deletion design.

8.2 Introduce PostgreSQL with migrations first

STEP 4.1

Schema, constraints, and Flyway

Owner Backend lead  |  Time 3–4 days  |  Depends 8.1 decisions

Goal. A reproducible schema with database-level guards against invalid result combinations, and migrations that build from an empty database.

SQL · core tables (illustrative; refine names to the course conventions)
CREATE TABLE users (
  id            UUID PRIMARY KEY,
  email         TEXT NOT NULL UNIQUE,
  password_hash TEXT NOT NULL,
  role          TEXT NOT NULL CHECK (role IN ('USER', 'ADMIN')),
  created_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
  disabled_at   TIMESTAMPTZ
);

CREATE TABLE refresh_tokens (
  id          UUID PRIMARY KEY,
  user_id     UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  token_hash  BYTEA NOT NULL UNIQUE,
  expires_at  TIMESTAMPTZ NOT NULL,
  revoked_at  TIMESTAMPTZ,
  created_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE scan_history (
  id               BIGSERIAL PRIMARY KEY,
  user_id          UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  created_at       TIMESTAMPTZ NOT NULL DEFAULT now(),
  hostname         TEXT NOT NULL,
  adapter_id       TEXT NOT NULL,
  status           TEXT NOT NULL CHECK (status IN ('SCORED', 'SIGNALS_ONLY', 'UNKNOWN')),
  trust_score      SMALLINT CHECK (trust_score BETWEEN 0 AND 100),
  verdict          TEXT,
  evidence_quality TEXT CHECK (evidence_quality IN ('LOW', 'ADEQUATE')),
  engine           TEXT NOT NULL CHECK (engine IN ('MODEL', 'SIGNALS_ONLY')),
  model_version    TEXT,
  reason_code      TEXT,
  CHECK (
    (status = 'SCORED'      AND trust_score IS NOT NULL AND verdict IS NOT NULL)
 OR (status = 'SIGNALS_ONLY' AND trust_score IS NULL AND verdict IS NULL)
 OR (status = 'UNKNOWN'      AND trust_score IS NULL AND verdict IS NULL AND reason_code IS NOT NULL)
  )
);

Rules

  • Use Flyway (or Liquibase if the course requires it) with versioned migrations. Never edit an applied migration; add the next one.
  • Keep DTOs separate from entities. The API never serializes an entity directly.
  • Index scan_history(user_id, created_at DESC) for the history query, and refresh_tokens(user_id) for revocation. Do not index fields that are never queried.
  • Store timestamps in UTC with TIMESTAMPTZ. Do not store a local timezone or a formatted date.
  • Add a database check that enforces the status/score/verdict consistency above. The application also validates, but the database is the last line of defence.
  • No column may hold review text, a review key, a URL, a fingerprint, or a reviewer identifier. A test queries information_schema.columns against a forbidden-name list.
Contract event

Auth and history add endpoints and error codes. Publish them as a contract release — for example contracts/v2/ for the account surface while the analysis schemas remain v1 — or promote the whole surface together. What you must not do is add UNAUTHORIZED and FORBIDDEN to the frozen v1 reason-code list without a version change. Record the choice in the decision register and update the contract tests.

Verify
  • Flyway migrates an empty database to the current schema with one command.
  • A second run is idempotent; no migration is applied twice.
  • The database rejects a scored row without a score and an unknown row with a score.
  • No forbidden column exists; the inspection test passes.
  • Deleting a user cascades refresh tokens and history, and the behaviour is tested.

8.3 Implement authentication and roles

STEP 4.2

Registration, login, refresh, logout, and the access matrix

Owner Backend lead  |  Time 5–7 days  |  Depends 4.1; contract decision

Goal. Passwords stored safely, tokens short-lived and revocable, roles enforced at the route level, and no account enumeration through error messages.

EndpointAccessBehaviour
POST /api/v1/auth/registerPublic, rate-limitedCreate a user with USER role; validate email and password policy; do not reveal whether an email exists in a way that enables enumeration beyond the necessary response.
POST /api/v1/auth/loginPublic, strict rate limitVerify Argon2id/BCrypt hash; return a short access token and a rotating refresh token; generic failure message.
POST /api/v1/auth/refreshRefresh tokenRotate the refresh token; detect reuse of a revoked token and revoke the family.
POST /api/v1/auth/logoutAuthenticatedRevoke the presented refresh token; access token expires naturally.
GET /api/v1/meAuthenticatedReturn id, email, role, created date. No password hash, no token.
GET /api/v1/historyAuthenticatedReturn only the caller’s rows; paginate; no text or URL.
DELETE /api/v1/historyAuthenticatedClear the caller’s history; idempotent.
DELETE /api/v1/meAuthenticated + re-authDisable/delete the account and cascade; record a content-free audit event.
/api/v1/admin/**ADMINRequire role; return 403 for USER and 401 for unauthenticated; never 404 to hide a route that is documented.

Password and token rules

  • Hash passwords with Argon2id via Spring Security’s encoder. If the native dependency is unavailable on the course environment, use BCrypt with cost 12 and document the choice. Never store or log the plaintext.
  • Access token: signed JWT, 15-minute lifetime, subject = user ID, role claim, issuer and audience set. Do not put email, name, or any review data in the token.
  • Refresh token: 256-bit random value, stored only as a hash, 30-day lifetime, rotated on every use. Reuse of an old token revokes the family.
  • Signing key from the environment, at least 256 bits. Never commit it. Rotate with a key ID so old tokens can be validated during a short overlap.
  • Login rate limit stricter than the general API limit (for example 5 attempts per minute per IP and per account), with a generic error message and a constant-time-ish path that does not reveal whether the account exists.
  • Logout revokes the refresh token. Client-side token deletion alone is not logout.

Extension token storage

  • Keep the access token in memory in the service worker. Keep the refresh token in chrome.storage.local only if refresh is implemented; never sync it.
  • Do not put tokens in content scripts, DOM attributes, URLs, or logs. Content scripts request an analysis through the worker.
  • On logout or account deletion, clear every token and every history entry.
  • If the extension is ever published to a store, review the privacy policy and host-permission justification. For the course, an unpacked build is sufficient.
401, 403, and 404 mean different things

401: no valid authentication. 403: authenticated but not allowed. 404: the resource does not exist or is not visible to this user. Do not return 404 for a documented admin route to “hide” it; that makes debugging impossible and does not add security. Do return 404 for another user’s history row to avoid confirming its existence.

Verify
  • A password hash is present in the database and the plaintext is absent from logs and responses.
  • An access token expires; an expired token returns 401; a refresh rotates and the old refresh token is rejected.
  • A USER calling an admin route gets 403; an unauthenticated caller gets 401.
  • User A cannot read, delete, or infer User B’s history; the response is 404 or an empty scoped list, never B’s data.
  • Login failures are rate-limited and use a generic message.
  • No token appears in a URL, a log, or a response body other than the token endpoint.

8.4 Implement history ownership and retention

STEP 4.3

Ownership filters, purge job, and deletion

Owner Backend lead  |  Time 2–3 days  |  Depends 4.2

Goal. Every history row is owned, every read is scoped, and old data disappears on schedule without a manual cleanup.

Rules

  • Never accept a userId from the client. Derive it from the authenticated principal.
  • Write history only after a result is returned, and only if the user has enabled server history. The analysis path must work with history disabled.
  • Store the same metadata as local history: timestamp, hostname, adapter ID, status, score/verdict when scored, evidence, engine, model version, reason code. No text, key, URL, IP, or user agent.
  • Purge rows older than the retention limit with a scheduled job. Log only the count and duration, never a row’s content.
  • Account deletion cascades history and refresh tokens. Audit entries keep an actor ID according to the audit policy, or are anonymized; decide and test.
  • Pagination is required. An unbounded history query is a denial-of-service vector and a privacy exposure.
Verify
  • Two users with history see only their own rows, including after pagination.
  • A history row cannot be created with a score and status UNKNOWN, or with no owner.
  • The purge job removes only expired rows and reports a count.
  • Deleting an account removes its history and refresh tokens.
  • The database contains no review text, key, URL, or fingerprint column.

8.5 Protect the admin surface

  • Phase 2’s dev-admin profile remains local-only, loopback, and unauthenticated for development. It is not the hosted admin.
  • Hosted admin routes require ADMIN and are enabled only when the account surface is enabled. A USER receives 403; an unauthenticated caller receives 401.
  • Admin actions that change state (enable/disable an adapter, purge a cache) write a content-free audit row: actor, action, target, timestamp, result. No request body.
  • Do not expose adapter authoring. The files remain versioned; the admin surface inspects and toggles local state only.
  • Test the boot guard again after security is added; a new filter chain must not accidentally expose the local profile through a different bind.

CHAPTER 09 · PHASE 5Deployment and expansion

A hosted demo is optional. If the project hosts, it must carry the controls the local design relied on: authentication, quotas, a private scoring network, TLS, secret management, monitoring, and a retention policy. Expansion is also optional, and each new site or language needs its own gate.

Phase exit condition

If hosted: the deployment reproduces the local behaviour with authentication, quotas, edge limits, HTTPS, secrets management, monitoring, backups, and a documented rollback. If not hosted: the decision is recorded. Expansion items each have fixtures, tests, and an honest unsupported state.

9.1 Choose the hosting shape

OptionFits whenTrade-off
Local onlyThe course accepts a local demo and the defense runs on one machine.No public exposure; simplest and safest. This is the baseline recommendation.
Single VPS + Docker Compose + CaddyA public demo is desired and one operator can manage patches and backups.Full control, moderate operational work; you own TLS renewal, updates, and backups.
PaaS with private services (Fly.io, Render, Railway)You want managed TLS and deploys with less server maintenance.Private networking and persistent Postgres cost money or impose limits; verify the scoring service is not publicly reachable.
KubernetesNot for this project unless the course requires it.Operational overhead far exceeds the product value.

The extension itself is distributed as an unpacked build or a ZIP for the course. A Chrome Web Store listing requires a developer account, a privacy policy, permission justification, and review; treat it as out of scope unless the course asks for it.

Rules

  • Only Caddy publishes host ports. Postgres and scoring are on the internal network with no host port.
  • Backend reaches scoring at http://scoring:8000 on the internal network; the browser never can.
  • Run containers as non-root. Drop Linux capabilities where possible; mount the filesystem read-only for the scoring image if the framework permits.
  • Pin image tags (including Postgres minor) and record the digests in the release. Do not deploy latest.
  • Set memory and CPU limits; the model’s memory footprint is part of the capacity plan.
  • Do not bake secrets into images. Pass them through the environment or Docker secrets.
Verify
  • docker compose up reaches healthy for db, scoring, backend, and edge from a clean volume.
  • Scoring and Postgres are unreachable from the host and from the public internet.
  • The backend starts only after scoring is healthy and the database is migrated.
  • Images run as non-root and contain no token or password.

9.3 Edge, TLS, secrets, and quotas

ControlRequirement
TLSHTTPS only; automatic certificate renewal; HSTS after confirming the domain. No mixed content.
Request sizeEdge limit at or below 131,072 bytes; backend repeats the check.
Rate limitEdge limit per IP plus application limit per IP/user. The application limit is the contract; the edge limit absorbs abuse.
CORSOnly the pinned packed extension ID and, if a web admin exists, its exact origin. No wildcard.
AuthenticationRequired for history and admin. Public analysis may remain available with quotas, or require auth if abuse is a concern; record the decision.
QuotasPer-user daily analysis quota and per-IP burst limit. Return 429 with a clear retry policy.
SecretsEnvironment or secret manager; never in the image, repository, or logs. Rotate on exposure.
HeadersStrict-Transport-Security, X-Content-Type-Options: nosniff, a restrictive Content-Security-Policy for any served HTML, and a referrer policy.
Caddyfile · shape, not a complete policy
trustloop.example.com {
    encode zstd gzip
    request_body {
        max_size 131072
    }
    header {
        Strict-Transport-Security "max-age=31536000; includeSubDomains"
        X-Content-Type-Options "nosniff"
        Referrer-Policy "no-referrer"
    }
    reverse_proxy backend:8080
}

Rate limiting is not a built-in Caddy directive in the standard distribution. Use a maintained plugin, a cloud edge (Cloudflare, a load balancer), or enforce the limit in the application and accept that the edge is not a shield. Do not invent a directive that silently does nothing.

9.4 Observability, backups, and rollback

AreaMinimum
LogsStructured JSON to stdout, shipped by the platform; content-free fields; request ID correlation. No bodies.
MetricsRequest rate, error rate, p50/p95/p99 latency, scoring readiness, model version, DB connections. Internal endpoint only.
Alerts5xx rate, scoring unready, latency above budget, disk above 80%, certificate expiry.
UptimeExternal check on /api/v1/health; alert on 503 for more than two minutes.
BackupsDaily Postgres dump, encrypted, retained per policy; test a restore, not just the backup.
MigrationsExpand/contract: add nullable columns and backfill before making them required; never drop a column in the same release that stops writing it.
RollbackKeep the previous image tags; reverse the application first, then the schema only if the migration is backward-compatible. A migration that cannot roll back needs a forward fix.
ReleaseImmutable image tag per release; deploy from the protected main; record the commit and image digest in the release notes.

9.5 Expansion rules

  • New adapter: manifest, selectors, supported-page description, fixtures, spike criteria, and an explicit unsupported state. It does not reuse the MVP adapter’s selectors silently.
  • New language: its own manual evaluation sample and gate. A translated UI is not model support. A failing gate returns UNKNOWN or a validated SIGNALS_ONLY.
  • New model: a new tl-text version, a new gate, a new artifact hash, and a model card update. No silent replacement of the artifact behind the same version.
  • New input type (rating, verified purchase, images): a new decision and a new model version; model v1 remains text-only.
  • Page aggregate: still prohibited. Mixed evidence must not be averaged into a product score.
  • Feature flags: avoid them unless a rollout requires one. A flag that changes score meaning is a hidden contract change.
