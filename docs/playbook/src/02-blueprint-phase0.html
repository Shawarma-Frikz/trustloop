If a file could belong to two components, it belongs in contracts/ if it defines the wire format, in docs/ if it records a decision, and in exactly one component otherwise. Shared runtime code between Java and Python is not a thing; shared meaning is a fixture.

3.4 Dependency direction

The repository is three processes, not three libraries. Dependencies point one way at runtime, and the contract is the only shared artifact. If an arrow in this table appears in code — an import, a shared database, a browser call to the scoring service — the boundary has been broken.

FromMay depend onMust never depend on
extension/contracts/, the public backend URLbackend/ source, scoring-service/, the database, an external AI API
backend/contracts/, the internal scoring URL, PostgreSQL in Phase 4extension/, browser APIs, a training dataset
scoring-service/contracts/, its artifact bundlethe backend, the database, the browser, live review text retention
contracts/Nothing at runtimeJava, Python, or JavaScript types; generated code checked in as hand-written
The test that catches drift

A contract test should fail if the extension ever imports from the backend source tree, if the scoring service imports a backend class, or if either component reads a fixture path outside TRUSTLOOP_CONTRACT_DIR. Boundaries survive by being testable, not by being documented.

CHAPTER 04 · PHASE 0Foundation and contract freeze

Phase 0 does not build the product. It removes the ways the project usually fails later: mismatched versions, an unfrozen contract, an unlicensed dataset, an adapter that was never tested, and an admin surface that leaks because “local-only” was a verbal promise.

Phase exit condition

Three empty components build and test; the professor-required backend layout exists; contract fixtures validate; dataset access and licensing are confirmed; the Amazon spike result and fallback are recorded; the charter is attached or waived; CI runs on a pull request; and every team member can explain the data flow and the score meaning.

STEP 0.6

Build the Python scoring skeleton

Owner ML lead  |  Time 2 hours  |  Depends 0.4

Goal. A FastAPI service on loopback with /health, /version, and a token-protected /score that fails closed until a model exists.

Do

  1. Create app/main.py, app/config.py, app/auth.py, app/schemas.py. Keep the files small; inference, explanation, language, and evidence modules arrive in Phase 1.
  2. Bind to 127.0.0.1:8000. Do not expose the service on all interfaces in local development.
  3. Read TRUSTLOOP_SCORING_TOKEN from the environment. If it is unset, /score returns a service-unavailable response and /health is not ready. Fail closed; never default to a known token.
  4. Use secrets.compare_digest for the token check, not string equality.
  5. Implement a lifespan hook that verifies the artifact hash and warms the model. In Phase 0 it sets a ready = false flag because no artifact exists. /health returns 503 until ready.
  6. Pin dependencies in requirements.txt and write requirements.lock from the clean environment.
Python · app/main.py — minimal readiness shape
from contextlib import asynccontextmanager
from fastapi import FastAPI

state = {"ready": False, "model_version": None}

@asynccontextmanager
async def lifespan(app: FastAPI):
    # Phase 1: verify artifact hash, load model, warm with sample texts.
    yield
    state.clear()

app = FastAPI(title="TrustLoop scoring", lifespan=lifespan)

@app.get("/health")
def health():
    from fastapi.responses import JSONResponse
    if not state["ready"]:
        return JSONResponse({"status": "DOWN", "modelVersion": None}, status_code=503)
    return {"status": "UP", "modelVersion": state["model_version"]}

Do — tests

  • /health is 503 before warm-up and 200 after a stubbed warm-up.
  • /score without a token is rejected; with a wrong token is rejected; with the correct token and no model returns the documented unavailable response.
  • The module imports without a model artifact present.

pytest -q

An unpacked extension gets an ID derived from its path. If the backend pins an extension origin for CORS, the ID can change when the folder moves. Do — freeze

  1. Open a single contract/v1-freeze PR containing schemas, fixtures, examples, and the validation tool. All three component leads review it.

If the contract is written after the backend, it describes the backend rather than the product. If it is written after the extension, it describes whatever the browser happened to send. Freezing first forces the three teams to agree on the score semantics, the unknown states, and the provenance rules while changing them is still cheap.

Owner ML lead with project lead  |  Time 1–2 days  |  Depends 0.1

Goal. No training starts on an unlicensed corpus, no French claim is made without a French evaluation set, and the model architecture choice has a default.

Do — dataset manifest

  1. For each candidate source, record: name, citation, URL, license, access date, allowed use, redistribution rule, language, label basis, known domain shift, and SHA-256 of the downloaded archive.
  2. Prefer public research corpora with explicit licenses: Ott et al. (2011, 2013) and, if useful, YelpChi or the GraphConsis Amazon dataset. Verify label granularity; do not treat reviewer-level flags as review-level labels.
  3. Do not commit the data if its license forbids redistribution. Commit the manifest and a download script; keep the data outside Git.
  4. Define the annotation codebook: organic, manipulated, uncertain/excluded; examples and edge cases; two annotators; Cohen’s kappa ≥ 0.60; adjudication by a third pass.
  5. Define the manual sample: 200–300 English reviews and 150–200 French reviews, sampled across products and lengths, labelled blind to model output. Record the sampling frame and seed.

Licensing is a gate, not paperwork

“Available online” is not a license. Record the specific terms and the allowed use. If a corpus’s license is unclear, treat it as unusable until clarified. A model trained on an unlicensed corpus cannot be shipped or published in the report without exposing the project to a licensing problem.

Verify
  • Every selected source has a license line and a hash in the manifest.
  • The annotation codebook and sample plan are written before any labels are collected.
  • D22–D24 are either resolved or explicitly defaulted, with the decision register updated.
  • No dataset is present in git status or in repository history.
STEP 0.12

Run the Amazon feasibility spike

Owner Extension lead  |  Time 1–2 days  |  Depends 0.7

Goal. Decide, with evidence, whether the narrow Amazon adapter is dependable enough to be the MVP path — or record a fallback before the team builds on it.

Do — choose three page variants

Pick three pre-chosen variants, for example a desktop product page with visible review cards, a dedicated reviews page, and a second locale or layout. Do not choose pages after seeing which ones work; that is selection bias.

Do — measure

  1. For each page, count the eligible reviews manually. An eligible review is rendered and not hidden inside the review container, with extractable text.
  2. Run the candidate selectors in DevTools. Count the cards the adapter would extract. Compare with the manual count.
  3. Record precision: extracted cards that are genuine, eligible reviews divided by all extracted cards. The pass threshold is at least 90% precision, not merely a high recall.
  4. Reload each page and repeat. Selectors must be stable across two consecutive loads.
  5. Require at least five eligible reviews per page. A page with two reviews cannot demonstrate batching or scrolling behaviour.
  6. Save sanitized HTML fixtures for supported and unsupported layouts. Remove names, account links, avatars, order data, and any personal information before committing.

  • Saved-page fixtures for the demo, keeping the adapter architecture. The product still demonstrates the end-to-end path, and the unsupported state remains honest.
  • An alternate site with the professor’s approval, recorded in the decision register before implementation.
Terms of service and privacy

Do not build a crawler. The spike is manual, limited, and for feasibility. Do not collect reviewer names, profiles, or account data, and do not store live page HTML with personal information. If the site’s terms prohibit the intended use, record that and use fixtures. A working adapter is not permission to ignore the terms.

Verify
  • Each criterion has a number and a date, not an impression.
  • A sanitized fixture exists for every supported and unsupported page variant used in the demo.
  • The adapter selector file is versioned and the adapter ID is amazon.reviews.v1.
  • If the spike failed, the fallback is recorded and Phase 1 scope is adjusted before coding starts.
