CHAPTER 05 · PHASE 1The analysis core

This is the phase that makes the project real: one supported page, one honest score, one explanation, and explicit states when the system cannot answer. No accounts. No database. The integration contract is already frozen, so the three teams can work in parallel against fixtures.

Phase exit condition

A supported page or fixture can be scanned end to end. Score, band, evidence quality, engine, model version, and explanation match the API result. Each supported language passes its gate or visibly uses SIGNALS_ONLY/UNKNOWN. Failure states are honest. Local history stores no content. Tests are green and warm p95 is within 1.5 seconds.

STEP 1.1

Create the DTOs and enums once per language

Owner All leads  |  Time 1 day  |  Depends Contract v1

Goal. Each component can parse every contract fixture and reject every invalid one, using types that mirror the schema exactly.

Java

5.3 Build the backend request pipeline

STEP 1.2

Request identity, size, rate, and CORS

Owner Backend lead  |  Time 2 days  |  Depends 1.1

Goal. Every request is identifiable, bounded, attributable to a client, and acceptable only from the extension origin.

Filter order

OrderFilterResponsibility
1CORSReject disallowed browser origins before other work. Preflight returns the allowed methods and headers.
2Request IDValidate or generate X-Request-Id, put it in MDC, echo it on the response.
3Payload sizeReject bodies over 131,072 bytes with 413 and PAYLOAD_TOO_LARGE.
4Rate limitEnforce 60 requests per minute per client IP; return 429 with Retry-After.
5ControllerValidate the DTO, call the service, return the response.

Request ID rules

Accept 1–64 characters matching [A-Za-z0-9-]. If absent or malformed, generate a UUIDv4. Set the response header even on errors. Put the ID in the logging context and remove it in a finally block so a reused thread never leaks another request’s ID.

Java · request ID filter, essential lines
String id = request.getHeader("X-Request-Id");
if (id == null || !id.matches("[A-Za-z0-9-]{1,64}")) {
    id = UUID.randomUUID().toString();
}
MDC.put("requestId", id);
response.setHeader("X-Request-Id", id);
try {
    chain.doFilter(request, response);
} finally {
    MDC.remove("requestId");
}

Size rules

  • Check Content-Length when present; reject immediately if it exceeds 131,072 bytes.
  • For chunked requests, wrap the input stream with a counting limiter and abort once the limit is crossed. A header check alone is not enough.
  • Also cap the JSON parser’s nesting depth and string length; a deeply nested body can exhaust memory even under the byte limit.
  • Return 413 with the error envelope, not a container-generated HTML error page.

Rate rules

  • Use an in-memory token bucket per client IP. The local default is 60 requests per minute. Bucket4j is a reasonable choice; a small ConcurrentHashMap implementation is acceptable if tested.
  • Do not trust X-Forwarded-For unless the backend is behind a known proxy and configured to read it. Otherwise a client can spoof the key.
  • Exclude nothing from the limit in production; health checks are local and cheap. In the performance test, raise the test-profile limit explicitly rather than special-casing an endpoint.
  • Emit Retry-After in seconds and keep the message generic: "Request rejected".

CORS rules

  • Allow only the configured extension origin(s), POST and GET, and the headers Content-Type and X-Request-Id.
  • Expose X-Request-Id and Retry-After so the extension can show and retry correctly.
  • Do not enable credentials in the MVP; there are no cookies. When authentication arrives in Phase 4, revisit this decision explicitly.
  • Pin the packed extension ID for any shared environment. A wildcard chrome-extension://* pattern is a development-only convenience and must be impossible to enable in production.
Java · CORS shape
CorsConfiguration c = new CorsConfiguration();
c.setAllowedOrigins(properties.allowedOrigins());
c.setAllowedMethods(List.of("POST", "GET", "OPTIONS"));
c.setAllowedHeaders(List.of("Content-Type", "X-Request-Id"));
c.setExposedHeaders(List.of("X-Request-Id", "Retry-After"));
c.setAllowCredentials(false);
c.setMaxAge(600L);
UrlBasedCorsConfigurationSource source = new UrlBasedCorsConfigurationSource();
source.registerCorsConfiguration("/api/**", c);
Verify
  • A malformed request ID is replaced; a valid one is echoed unchanged.
  • A 131,073-byte body returns 413 and the error envelope.
  • The 61st request in a minute returns 429 with Retry-After.
  • A preflight from an unlisted origin fails; the configured extension origin succeeds.
  • No response includes a stack trace or internal class name.

5.4 Call the scoring service safely

STEP 1.4

Scoring client, timeout, and atomic failure

Owner Backend lead  |  Time 2 days  |  Depends 1.3; scoring stub

Goal. One attempt, one token, one request ID, a three-second ceiling, and an all-or-nothing batch when the service fails.

Client configuration

  • Base URL from TRUSTLOOP_SCORING_URL; token from TRUSTLOOP_SCORING_TOKEN; expected model version from configuration.
  • Connect timeout 500 ms; read timeout 3,000 ms. Do not use an infinite or default timeout.
  • Send X-Internal-Token and the incoming X-Request-Id. Never send the browser origin or any client identifier.

Derive the transient duplicate flag

Mark batchDuplicate = true when another review in the same batch shares the normalized hash. Never store the hash, the text, or the flag. The flag is a within-batch observation, not a claim about the page or the world.

5.5 Build the data pipeline

STEP 1.6

Acquire, normalize, deduplicate, and split

Owner ML lead  |  Time 4–6 days  |  Depends D22; licensed data

Goal. A reproducible, leakage-free dataset with a manifest, stable splits, and no live review text.

Pipeline stages

  1. Acquire. Download each licensed source into data/raw/<source>/ using a script, never by hand. Record the URL, access date, license, and SHA-256 in the manifest.
  2. Normalize. Apply Unicode NFKC; strip HTML tags; remove zero-width and control characters except newline/tab; collapse whitespace; keep punctuation and case for the feature pipeline. Compute the word count after normalization, using the same definition as the service.
  3. Map labels. Convert each source’s label to organic/manipulated using an explicit table. Mark uncertain or unlabelable items and exclude them from training and from the primary metric. Never merge a reviewer-level flag into a review-level label without documentation.
  4. Filter. Drop training items below 20 words to match deployment; record how many were dropped. Do not silently keep them and then evaluate only on long reviews.
  5. Deduplicate. Use MinHash with five-word shingles at a 0.80 similarity threshold, or cosine similarity on normalized text for a smaller corpus. Remove near-duplicates across the entire corpus before splitting.
  6. Split by group. Group by product or source item, never by individual review. Assign groups to train/dev/calibration/test so no group appears in two splits. Verify the split with an assertion, not a visual scan.
  7. Balance report. Record class counts per split, per source, and per language. Do not resample unless the method and its effect are documented.
  8. Freeze. Write split-manifest.json with group IDs, item counts, seeds, and hashes. Training reads the manifest; it does not re-split on every run.

Manual evaluation sample

  • Draw 200–300 English and 150–200 French reviews across products, lengths, and label balance. Record the sampling frame, date, and seed.
  • Two annotators label blind to the model, using the codebook. Report Cohen’s kappa; below 0.60, revise the codebook and relabel before using the sample.
  • Adjudicate disagreements with a third pass. Keep the raw labels and the adjudicated label; the adjudicated one drives the gate.
  • If part of the sample is used for adaptation or threshold tuning, report the untouched held-out portion separately and compute the gate only on it.
  • Store only review IDs and labels in the repository. Do not commit reviewer names or identifiers.
Leakage is the quiet failure

A random review split puts near-duplicate reviews on both sides of the evaluation and inflates every metric. A group split with cross-split deduplication is not optional because the numbers look better without it. Assert in code that no group ID appears in two splits, and that no MinHash cluster crosses a split boundary.

Verify
  • The pipeline runs from raw data to split manifest with one command per stage.
  • No group ID appears in more than one split; the test asserts it.
  • Class and language counts are reported per split; no split has an empty class.
  • The manifest contains a license and hash for every source.
  • No live TrustLoop text, reviewer name, or URL is in the corpus.

5.6 Train the baseline and calibrate it

STEP 1.7

Fit the pipeline and choose calibration on dev

Owner ML lead  |  Time 3–5 days  |  Depends 1.6

Goal. A deterministic, CPU-friendly model with calibration fitted on a split that was never used for tuning, and metrics that can be reproduced.

Baseline

Python · baseline shape
word = TfidfVectorizer(ngram_range=(1, 2), min_df=2,
                       max_features=200_000, sublinear_tf=True)
char = TfidfVectorizer(analyzer="char_wb", ngram_range=(3, 5),
                       min_df=3, max_features=200_000)
features = FeatureUnion([("word", word), ("char", char)])
clf = LogisticRegression(C=1.0, class_weight="balanced",
                         max_iter=2000, random_state=42)

Training protocol

  1. Tune only on dev: C, min_df, and feature caps. Keep the grid small; a large grid on a small corpus overfits the dev split and wastes the schedule.
  2. Use class weights rather than duplicating the minority class. If resampling is used, document it and apply it to training only.
  3. Fit calibration on the dedicated calibration split: Platt scaling for small samples, isotonic only when the split is large enough to support it. Choose the method by dev reliability, then report on test.
  4. Set random seeds and single-threaded BLAS for deterministic outputs (OMP_NUM_THREADS=1, OPENBLAS_NUM_THREADS=1). Record the environment.
  5. Touch the test split once per candidate. Report the result even when it is disappointing; do not keep tuning until it passes.

Score mapping, implemented once

Put the score and band functions in one module used by training, evaluation, and serving. Unit-test every boundary and a half-up case such as p_organic = 0.705 → 71.

ScoreBand code
0–19STRONG_MANIPULATION_SIGNALS
20–39LIKELY_MANIPULATED

55–69MIXED_SIGNALS

Calibration is not prevalence

Public corpora are often class-balanced by construction. A score of 73 means the model estimates 73% organic likelihood on the evaluation distribution; it does not mean 73% of Amazon reviews are organic, and it does not mean 27% are fake. Put this in the model card, the report, and the panel copy.

Metrics to compute

  • AUROC and AUPRC for the manipulated class, with 95% bootstrap confidence intervals.
  • F1 for manipulated at p_organic = 0.50, reported as an operating point, not a deployed threshold.
  • ECE with 10–15 bins, Brier score, and a reliability curve stored with the metrics.
  • Per-language results and overall results, plus public-dataset transfer results separately.
  • Class balance, sample size, and CI method beside every number.
Verify
  • Two runs with the same seed and environment produce identical metrics and identical predictions on a fixed sample.
  • Calibration was fitted only on the calibration split.
  • The test split was used once for the reported candidate.
  • Every metric has a confidence interval and a sample size.
  • The score/band boundary tests cover 19/20, 39/40, 54/55, 69/70, 84/85, 0, and 100.

5.7 Build the explanation

STEP 1.9

Attribute the linear model and aggregate signals

Owner ML lead  |  Time 2–3 days  |  Depends 1.7

Goal. At most five stable, human-readable signals with direction, optional validated contribution, and no quoted review text.

Method

  • For the linear baseline, a feature’s contribution is its coefficient for the predicted class multiplied by its normalized value. Negative values push toward manipulated; positive values push toward organic, depending on the class encoding. Document the sign convention once.
  • Aggregate token features into the named signal groups in Appendix E. Some groups are model features; others are rule-based observations (for example, within-batch duplication) and may be qualitative.
  • Normalize signed contributions across the full feature set so the total absolute contribution is 1. Return the top five with their original normalized values. Do not renormalize the returned subset; that would make a weak signal look strong.
  • If a signal cannot be attributed stably, omit its numeric contribution and return the qualitative summary. The contract allows this; the UI must handle it.
  • Never quote the review text, a name, a URL, or a personal detail in a signal summary. Summaries are fixed templates from the copy deck.
Python · attribution shape
# x: sparse feature vector for one review; coef: linear coefficients
raw = x.multiply(coef).tocsr()          # signed per-feature contribution
total = abs(raw).sum()
normalized = raw / total if total else raw
# aggregate by taxonomy group, keep the signed sum per group,
# sort by absolute value, return at most five

Stability gate

For a fixed set of inputs, compare the top-five signal sets across three bootstrap-trained models or three seed variations. The mean Jaccard must be at least 0.80. Run the same input twice with the same artifact and compare the full result hash; it must be identical. If stability fails, return qualitative signals or keep the linear model and omit the numeric contribution.

Verify
  • Top-five stability is ≥ 0.80; the test stores the per-input Jaccard values.
  • Two identical requests produce byte-identical result JSON (excluding the request ID).
  • No signal summary contains a substring of the input text; a test uses a sentinel phrase.
  • Contributions, when present, sum to at most 1 in absolute value and are not renormalized after top-five selection.
  • The panel can render a signal with no contribution without showing a zero or an empty bar.

    // Host and path checks only; no fetch, no page-wide scrape.
    return /(^|\.)amazon\.(com|ca|co\.uk)$/.test(location.hostname);
  },
  findCards(root) {
    return [...root.querySelectorAll("[data-hook='review']")];
  },
  extract(card) {
    const text = card.querySelector("[data-hook='review-body']")?.innerText ?? "";
    const stableId = card.getAttribute("data-review-id") ?? null;
    return { text, stableId };
  }
};

The selectors above are placeholders. The real ones come from the Phase 0 spike and live in adapters/amazon.reviews.v1/selectors.json, versioned with the adapter. A selector change is an adapter version change if it changes which cards are considered reviews.

Eligibility

JavaScript · eligibility check, essential lines
export function isEligible(card) {
  const style = getComputedStyle(card);
  if (style.display === "none" || style.visibility === "hidden") return false;
  if (card.closest("[aria-hidden='true']")) return false;
  const rect = card.getBoundingClientRect();
  if (rect.width === 0 || rect.height === 0) return false;
  return normalizeText(extractText(card)).length > 0;
}

Viewport intersection only schedules work; it does not decide eligibility. Two users scanning the same DOM state must see the same review set regardless of scroll position. This prevents the score set from depending on how far someone happened to scroll.

Deduplication

  • Use the adapter-provided stable card ID when present. Map it to a random, opaque reviewKey held in memory for the page session.
  • When no stable ID exists, hash the normalized text with a per-session random salt. The hash and the salt never leave memory.
  • Use the DOM ordinal only as a tie-breaker, never as the primary key; virtualized lists reuse nodes and reorder them.
  • Discard the map on navigation. Never write a key, a hash, or a salt to local history, storage, or a server.
  • Track submitted keys in a set so scrolling and mutation do not resubmit the same review. A manual retry for an unavailable batch may resubmit, but an automatic loop may not.

Scanning loop

  • Debounce DOM mutations by 750 ms. Enforce a minimum interval of 2,000 ms between scans to avoid a mutation storm.
  • Observe the adapter’s container, not the whole document. Disconnect the observer on navigation and reinitialize on the new page.
  • Use an IntersectionObserver to prioritize visible cards, but build the eligible set from the DOM, not from the viewport.
  • Batch up to 10 unscored eligible reviews. Send batches sequentially; do not fire ten parallel requests.
  • Abort an in-flight request on navigation. The service worker enforces a 6-second ceiling with AbortController; the backend ceiling is 4 seconds.
Verify
  • A hidden review is excluded; a visible review is included; a zero-size card is excluded.
  • Scrolling does not resubmit a review; a DOM mutation does not resubmit an already-submitted key.
  • A batch never exceeds 10, even when 25 reviews are eligible.
  • The dedup map is empty after navigation, and no key or hash exists in storage.
  • An unsupported layout yields UNSUPPORTED_PAGE, never a generic scrape.
STEP 1.12

Service worker network layer and message protocol

Owner Extension lead  |  Time 2 days  |  Depends 1.11; backend endpoint

Goal. One place performs network calls, generates the request ID, enforces the timeout, and maps transport failures to explicit UI states.

Protocol

MessageDirectionPayload
ANALYZE_BATCHContent → worker{ adapterId, languageHint?, reviews:[{reviewKey,text}] }
ANALYZE_RESULTWorker → content{ ok:true, data } or { ok:false, reasonCode }
HISTORY_*Popup/content → workerMetadata-only reads, clear action, opt-in toggle.

Network rules

  • Generate a UUIDv4 X-Request-Id per batch. Do not reuse it across retries; a retry is a new request.
  • POST to the backend base URL from configuration, with Content-Type: application/json and the six-second abort timeout.
  • Validate the response shape before sending it to the content script. A malformed response becomes SCORING_UNAVAILABLE.
  • Do not retry automatically. The panel offers a manual retry; the user decides.
  • Never log review text, keys, or the full request body. Log only batch size, status, latency, and request ID.
Why the service worker calls the API

The content script lives in the page’s origin and can inherit page CSP restrictions; the service worker has the extension origin and a single network policy. Keeping the tokenless public call in one place also makes timeout, request ID, and response validation testable without a DOM.

Verify
  • A 3.5-second service delay surfaces as SCORING_TIMEOUT in the UI, not a spinner forever.
  • A 500 response surfaces as SCORING_UNAVAILABLE with a retry action.
  • The request ID sent to the backend equals the ID in the response and in the logs.
  • No automatic retry occurs after a failure; a test asserts one call.
  • The worker rejects a response with a score but no model version.

5.10 Render the badge, panel, and states

Badge

5.11 Add local history

STEP 1.14

Opt-in, metadata-only history

Owner Extension lead  |  Time 1 day  |  Depends 1.13

Goal. A useful recent-history view that cannot become a store of review content.

Policy

  • Off by default. The popup explains what is stored before the user enables it.
  • Store one entry per analyzed result: timestamp, hostname (not URL), adapter ID, status, score/verdict when scored, evidence quality when present, engine, model version when present, reason code when unknown.
  • Never store review text, review keys, reviewer identifiers, full URLs, page titles, or a persistent text fingerprint.
  • Cap at 100 entries or 30 days, whichever is reached first. Prune on write and on open.
  • Keep it in chrome.storage.local; never sync it. Provide a clear-history action with confirmation.
  • Disabling history stops writes and offers to clear existing entries; do not silently retain them.

5.12 Prove observability and privacy

STEP 1.15

Request ID tracing and content-free logs

Owner Backend lead + QA  |  Time 1–2 days  |  Depends 1.5, 1.10, 1.12

Goal. One scan can be followed from extension to backend to scoring service by request ID, and a sentinel review text cannot be found anywhere in logs or storage.

Log events

EventWhenAllowed fields
api.request.receivedAfter validation.requestId, adapterId, reviewCount, httpStatus
api.scoring.completedService response validated.requestId, reviewCount, status, engine, modelVersion, latencyMs
api.scoring.failedTimeout, connection, malformed, version mismatch.requestId, reasonCode, latencyMs
api.response.sentResponse written.requestId, httpStatus, resultStatuses, latencyMs

Forbidden everywhere: review text, review key, URL, hostname, reviewer name, request or response body, raw exception stack trace in public logs, internal token, and model coefficients that could reconstruct text. Use a log pattern with the request ID in MDC; never concatenate the body into a message.

The sentinel test

  1. Send a review containing a unique marker, for example SENTINEL_REVIEW_TEXT_9F3A.
  2. Capture backend logs with an in-memory appender; capture service logs with caplog.
  3. Assert the marker is absent from every log line.
  4. Run the extension scan, dump chrome.storage.local, and assert the marker and the review key are absent.
  5. Capture network requests in DevTools; assert the only destination is the configured backend, with no external AI or analytics host.
Framework logs leak by default

Spring can log request details at DEBUG, and a validation error can include the rejected value. Keep production at INFO, disable request logging, and ensure the exception handler never logs the DTO. A privacy test that only greps the application logger will miss a framework logger; capture the root logger.

Verify
  • The same request ID appears in the extension console, backend log, and scoring-service log for one scan.
  • The sentinel marker is absent from both services’ logs.
  • Storage contains no text, key, URL, or hash.
  • No outbound request goes anywhere except the backend.
  • Error logs contain a reason code, not an exception message with request content.

5.13 End-to-end demo and performance

STEP 1.16

Run the real path and measure it

Owner All  |  Time 2 days  |  Depends 1.10–1.15

Goal. One command sequence starts the system; one supported page produces honest results; the warm latency budget is measured, not assumed.

Run order

  1. Start the scoring service on 127.0.0.1:8000 with the artifact and token set. Wait for /health to return 200.
  2. Start the backend on 127.0.0.1:8080 with the same token and the expected model version. Confirm /api/v1/health is 200 and /api/v1/version matches.
  3. Build the extension and load dist/ unpacked. Confirm the backend CORS allowlist contains its origin.
  4. Open the supported fixture or page. Scan. Confirm badges appear beside the correct reviews, not shifted by one card.
  5. Open one scored panel, one low-evidence panel, and one unknown state. Confirm the text and provenance.
  6. Stop the scoring service. Scan again. Confirm every result is unavailable with a retry action, not a score.
  7. Restart scoring, retry, and confirm recovery.

Performance method

  • Use the reference environment: 4 vCPU, 8 GB RAM, CPU only. If your laptop is faster, report the difference; do not claim the gate on better hardware.
  • Generate 10 reviews of 2,000 characters, mixed English. Warm with at least 20 batches. Measure 100 batches; report p50, p95, and p99.
  • Measure the scoring service alone and the backend end to end. The service gate is p95 ≤ 1.5 s; the backend must finish within its 4 s ceiling, including validation.
  • Raise the rate limit only in the test profile; do not disable it in the default profile.
  • Record the artifact hash, model version, machine specification, and command in the evidence file.

If latency fails

  1. Profile vectorization versus prediction; character n-grams often dominate.
  2. Batch vectorize the ten reviews instead of looping per review.
  3. Reduce feature caps or character n-gram range, then re-run the gate; a performance change that alters the model is a MINOR version.
  4. Do not raise the timeout to make the number pass; the timeout hierarchy is part of the contract.
Verify
  • The demo runs from a clean start using only the README/runbook.
  • Badges attach to the matching review after a DOM mutation and a scroll.
  • A stopped service produces unknown states and a working manual retry.
  • Warm p95 for 10 reviews is ≤ 1.5 s on the reference environment.
  • The timeout hierarchy is observable: service 3 s, backend 4 s, extension 6 s.
