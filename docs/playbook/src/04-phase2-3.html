CHAPTER 06 · PHASE 2Breadth without risk

Phase 2 adds only what the MVP can absorb without changing the score’s meaning: another supported page, adapter packaging, and a local inspection surface that cannot be reached from a network. If time is short, this phase can legitimately ship with one adapter and the admin surface only. It must not introduce a database, runtime adapter authoring, or an unauthenticated shared surface.

Phase exit condition

All agreed non-auth flows work locally. The default profile has no admin surface. The dev-admin profile binds to loopback and refuses to start otherwise. Adapter files are versioned, fixtures exist, and no database was introduced without a persistence decision.

6.1 Decide whether to add a second adapter

A second adapter is optional. It is worth doing only when the first adapter is stable, the model’s inputs do not change, and the new page type can meet the same evidence standard. It is not worth doing to make the demo look broader.

QuestionRequired answer before starting
Is the first adapter stable?Phase 1 gate passed; no selector regression in the last two weeks.
Does the new page add a distinct surface?Yes: a different layout, domain, or review presentation — not a cosmetic variant.
Can it meet the spike criteria?Three variants, ≥5 eligible reviews, ≥90% precision, stable across two loads.
Does it require new model inputs?No. If it does, the model changes and needs a new gate; that is not Phase 2 scope.
Are the terms acceptable?Recorded and compatible with a manual/demo use; no crawler.
Is there time to do it without cutting tests?Yes. Otherwise skip the adapter and finish the admin surface.
No generic fallback

A second adapter is a second explicit contract with the page. If a selector is not understood, the result is an unsupported state. A generic page scraper would send navigation, ads, and unrelated text to the model, which is both a privacy failure and a meaningless score.

6.2 Package adapters as versioned files

STEP 2.1

Manifest, selectors, supported pages, fixtures

Owner Extension lead  |  Time 2–4 days  |  Depends 6.1 decision; Phase 1 gate

Goal. Each adapter is a self-contained, inspectable directory with no runtime authoring and no hidden configuration.

Text · extension/adapters/<adapterId>/
manifest.json          id, version, supported hosts, entry module, status
selectors.json         container, card, body, stable-id, exclusions
supported-pages.md     what is supported, what is not, known variants
fixtures/              sanitized supported and unsupported HTML
README.md              owner, last verified date, spike result link

Manifest rules

  • The adapter ID follows site.surface.vN and never changes for a compatible selector update.
  • A breaking change to eligibility or extraction increments the adapter version; the old adapter remains until the new one passes its fixtures.
  • The manifest lists exact hosts. No wildcard top-level domain and no <all_urls>.
  • The registry is assembled at build time from the versioned files. The extension does not fetch adapter code at runtime.
  • Enable/disable is local UI state in the admin surface, not a write to these files.

Fixture rules

  • Every supported variant has a fixture; every known unsupported variant has one too.
  • Sanitize fixtures: remove names, avatars, account links, order IDs, and any personal data. Keep the DOM structure needed to test selectors.
  • A fixture test asserts the exact set of extracted review texts and stable IDs; a selector change that silently adds a navigation block fails the test.
  • Fixtures are not a license to store live pages. They are minimal, sanitized reproductions.
Verify
  • The adapter registry contains only bundled, versioned adapters.
  • Each adapter has at least one supported and one unsupported fixture.
  • An unsupported fixture produces UNSUPPORTED_PAGE, not an empty batch or a generic scrape.
  • No fixture contains a reviewer name, avatar, URL, or order identifier.
  • Disabling an adapter in the local admin UI does not modify any file in extension/adapters/.

6.3 Build the local dev-admin profile

STEP 2.2

Inspection, in-memory toggles, and loopback enforcement

Owner Backend lead  |  Time 3–4 days  |  Depends Phase 1 backend stable

Goal. A local-only surface for inspecting bundled adapters and content-free metrics, enforced by profile, bind address, and a startup guard — not by a sentence in the README.

Profile boundary

ProfileAdmin behaviourBind
defaultNo admin beans, no admin routes; /api/v1/admin/** returns 404.127.0.0.1 by default.
dev-adminInspection endpoints, local toggles, in-memory metrics; warning at startup; no authentication.Must be loopback; boot guard refuses anything else.
testDeterministic stubs; no external calls; admin tests use the test profile or a dedicated slice.No network required.

Endpoints

EndpointPurpose
GET /api/v1/admin/adaptersList bundled adapter IDs, versions, supported pages, fixture paths, and enabled state.
GET /api/v1/admin/adapters/{id}Inspect selectors, supported-page description, and fixture inventory.
POST /api/v1/admin/adapters/{id}/enabledToggle local enablement in memory; reset on restart; no file write.
GET /api/v1/admin/metricsContent-free counters: requests by status, results by status/reason, scoring latency buckets, model version.

A minimal HTML page can render the same data, but JSON plus a simple local page is enough. Do not build a dashboard framework. The admin surface exists to inspect and demonstrate isolation, not to become a second product.

Boot guard

  1. application-dev-admin.properties sets server.address=127.0.0.1.
  2. A startup component active only under dev-admin reads the effective bind address. If it is unset, empty, 0.0.0.0, or a non-loopback address, it throws and the application refuses to start.
  3. Accept 127.0.0.1, ::1, and localhost after normalization. Do not accept a hostname that merely resolves to loopback without checking.
  4. Log a clear warning at startup: local-only, no authentication, never expose through a tunnel.
“Local-only” must be mechanical

A profile that defaults to loopback but can be overridden with --server.address=0.0.0.0 is not local-only. The guard converts the promise into a startup failure. Test it by launching with a non-loopback bind and asserting the context fails.

Metrics

  • Counters: requests received, responses by HTTP status, results by status, unknowns by reason code, scoring latency buckets, model version.
  • No per-review content, no review key, no URL, no adapter-specific page identifier beyond the adapter ID.
  • In-memory only; reset on restart. Persistence would require a retention and ownership decision, which is Phase 4 work.

Access rules

  • No authentication in this phase, because the surface is loopback-only and local. It must never be exposed through a tunnel, reverse proxy, or shared network.
  • When authentication arrives in Phase 4, admin functions require an authenticated admin role before any shared or hosted use. The dev-admin profile remains a local development tool.
  • Do not add runtime adapter authoring. Editing adapter files at runtime requires persistence, audit, and ownership rules that do not exist yet.
Verify
  • Default profile: every /api/v1/admin/** route returns 404, including a made-up subpath.
  • dev-admin with a loopback bind starts and lists bundled adapters.
  • dev-admin with a non-loopback bind fails to start with a clear error.
  • A toggle changes the response until restart, then resets to the bundled default.
  • The adapter directory hash is unchanged before and after a toggle.
  • Metrics contain no text, key, URL, or hostname.

CHAPTER 07 · PHASE 3Evidence, accessibility, and quality

Phase 3 is where the project becomes defensible. The model is evaluated on held-out data, the explanation is tested for stability, the interface is audited with a keyboard and a screen reader, and the privacy claims are re-proven against the final build. Nothing new is added except evidence and fixes.

Phase exit condition

The held-out evaluation and model card are complete, accessibility checks pass, performance and timeout behaviour are confirmed on the reference environment, privacy and security are re-audited, and the traceability evidence is ready for the report and defense.

7.1 Run the held-out evaluation

STEP 3.1

Evaluate the frozen artifact once, honestly

Owner ML lead  |  Time 3–5 days  |  Depends Phase 1 artifact

Goal. A reproducible evaluation report on the untouched manual sample, with confidence intervals and a per-language gate decision.

Protocol

  1. Freeze the artifact and the held-out sample manifest. Record both hashes in the report.
  2. Run the evaluation script against the artifact. Do not retrain, tune, or select a threshold on the held-out data.
  3. Report AUROC, AUPRC, F1 at 0.50, ECE, Brier, reliability curves, class balance, and sample size, overall and per language.
  4. Compute 95% bootstrap confidence intervals (at least 1,000 resamples) and state the resampling unit (review or group).
  5. Report public-dataset transfer results separately. They are evidence about transfer, not the gate.
  6. Report the gate result as pass/fail per language. If a language fails, state the fallback and update D23.
  7. Include the disappointing numbers. A report that only shows the best candidate is not an evaluation.
Report itemWhy the reviewer needs it
Dataset manifest and split countsShows the evaluation is group-disjoint and licensed.
Label protocol and kappaShows the labels are not one person’s opinion.
Reliability curveShows calibration, not only ranking.
Confusion matrix at 0.50Makes the operating point concrete.
Per-language tablePrevents an overall average from hiding a failing language.
Transfer tableSeparates in-domain evidence from cross-domain claims.
Failure examplesShows where the model is weak without quoting live reviews.
Verify
  • A clean rerun on the same artifact and sample reproduces the metrics within the stated tolerance.
  • Every metric has a confidence interval and a sample size.
  • The gate decision is per language and matches metrics.json.
  • No live review text or reviewer identifier appears in the report.
  • The calibration scope limitation is stated in plain language.

7.2 Test explanation stability and UI mapping

STEP 3.2

Prove the panel matches the result

Owner ML lead + extension lead  |  Time 2 days  |  Depends 3.1

Goal. The top-five signal set is stable, deterministic, and rendered without adding claims the API did not make.

Tests

  • Top-five Jaccard ≥ 0.80 across three bootstrap models for a fixed input set; store per-input values, not just the mean.
  • Identical input and artifact produce an identical result hash across repeated runs.
  • A UI mapping test feeds a fixture into the panel and asserts every visible string comes from that fixture: score, band, evidence, engine, model version, signal summaries, and directions.
  • A signal with no contribution renders without a bar, a zero, or a percentage.
  • A sentinel phrase in the review text never appears in the panel, including tooltips and aria-labels.
  • The panel never says “proof,” “fake,” “bot account,” “fraud,” or “verified.” A string test enforces the forbidden list in both languages.
Explanation is part of the contract

If the panel invents a reason, the product lies even when the score is correct. The panel is a renderer, not an analyst: it displays the API’s signals, direction, evidence, and provenance, and nothing else.

Verify
  • Stability and determinism gates pass and are linked in the evidence file.
  • Every visible panel field is traceable to a fixture field.
  • No raw text, name, or URL appears in a signal summary.
  • Forbidden claim strings are absent from both language files.

7.7 Finalize the model card and reproducibility

STEP 3.5

Write the model card a reviewer can use

Owner ML lead  |  Time 1–2 days  |  Depends 3.1–3.2

Goal. The model’s intended use, data, metrics, limitations, and version are documented in one place, and a clean rerun reproduces the metrics.

Model card sections

  1. Intended use and out-of-scope use.
  2. Training and evaluation data, licenses, hashes, split method, and label protocol.
  3. Supported languages and per-language caveats.
  4. Metrics with confidence intervals, reliability curve, and gate result.
  5. Explanation method, signal taxonomy, and stability result.
  6. Known limitations: domain shift, label noise, class-balanced calibration, short text, sarcasm, translation artifacts, adversarial and LLM-generated text.
  7. Version, date, artifact hash, and the decision-register entries that authorized the release.
Reproduction check

Create a clean Python environment from requirements.lock on a second machine or a fresh virtual environment. Run the evaluation script against the published artifact and split manifest. The metrics must match metrics.json; if they do not, report the discrepancy and the cause rather than hiding it.

Verify
  • The model card is complete and linked from the README and the report.
  • The artifact hash and model version appear in the card and in /api/v1/version.
  • A clean rerun reproduces the metrics within the stated tolerance.
  • Every limitation has a mitigation or an explicit acceptance.
