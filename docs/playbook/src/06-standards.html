CHAPTER 10Cross-cutting standards

These rules apply in every phase. They are the difference between three components that happen to work together and a system a reviewer can trust. When a standard conflicts with a deadline, cut scope — not the standard.

10.1 Errors

There are two error surfaces: per-result states inside a successful batch, and request-level errors with a separate envelope. Do not collapse them. A timeout on one batch is not a 500 for the whole API, and an invalid request is not a per-review unknown.

Rules. The message is a fixed, safe string; the request ID is always present. No stack trace, exception class, SQL fragment, internal URL, token, or review text crosses the public boundary. The internal cause is logged content-free. A per-result unknown is never encoded as 0, 50, or null. A request-level error never contains a partial results array.

10.2 Logging and privacy

AllowedForbidden
timestamp, level, event, requestId, adapterId, reviewCount, status, reasonCode, engine, modelVersion, latencyMs, httpStatusreview text, review key, URL, hostname, reviewer name, request/response body, token, password, email, raw stack trace in public logs, model coefficients that reconstruct text

Use one structured event per lifecycle step: api.request.received, api.scoring.completed, api.scoring.failed, api.response.sent. Put the request ID in MDC and include it in every line for that request. Remove it in a finally block.

Log levels: INFO for lifecycle and failures that the operator must see; WARN for degraded readiness, rate-limit surges, and version mismatch; ERROR for unexpected failures; DEBUG only locally and never with bodies. Do not enable framework request logging in a shared environment. A validation exception must not log the rejected DTO.

Log retention is part of the privacy policy. Keep application logs long enough to debug a demo (for example 7–14 days) and no longer than necessary. Hosted logs inherit the provider’s retention; record it. Logs are content-free, so retention is less sensitive, but request IDs and timestamps are still operational data.

10.5 Accessibility standard

Target WCAG 2.2 AA for the extension UI and any admin page. The critical commitments:

  • Every interactive element is keyboard operable, with a visible focus indicator that is not obscured.
  • The badge is a button with an accessible name containing score, band, evidence, and engine.
  • The panel has a name, manages focus, closes on Escape, and returns focus to its trigger.
  • Status changes use a polite live region; do not announce every card repeatedly.
  • Verdicts do not rely on colour; text and shape carry the meaning.
  • Text contrasts at 4.5:1; large text and essential graphics at 3:1.
  • 200% zoom and 320 CSS px reflow without horizontal scrolling for the panel.
  • French content is marked with lang="fr".
  • Motion respects prefers-reduced-motion; no essential animation.
  • Targets are at least 24×24 CSS px, preferably 44×44 for touch.

Test data. Use synthetic review text and sanitized fixtures. Never commit live review text or reviewer identifiers. A sentinel phrase is useful precisely because it is unique and easy to search for in logs and storage.

CI expectations. Every pull request runs the component tests and the contract tests. A model gate is a manual or scheduled workflow with the published artifact; it is not retrained on every PR. A failing test blocks merge; a skipped test is not a pass.

10.8 Definition of Done

  • The behaviour matches the issue’s acceptance checks, not just the happy path.
  • A test fails without the change and passes with it.
  • Contract impact assessed; version bumped and fixtures updated if needed.
  • Privacy impact assessed: no new text, key, URL, or fingerprint in logs or storage.
  • Security impact assessed: validation, authorization, secrets, error exposure.
  • Accessibility checked for any UI change.
  • CI green, including the contract workflow.
  • Reviewed by the code owner; conversations resolved.
  • Docs/evidence updated; no leftover TODO that hides a broken path.
  • No secret, dataset, or build output added to Git.

10.9 The five-minute self-review

Do this before you request review. It is cheaper than a review cycle and it catches the failures reviewers should not have to find.

  1. Re-read the issue’s acceptance checks and map each one to a test or a manual step.
  2. Run the new test without the fix, then with it. If the result does not change, the test proves nothing.
  3. Read your own diff in the GitHub “Files changed” view, not in the editor. Editors hide omissions.
  4. Check the contract, privacy, and security boxes honestly; write one sentence for each where the answer is not obvious.
  5. Write the PR paragraph: what changed, why, what you verified, and what you did not.

Blocks the merge

  • A failing test or a gate that was not run.
  • Contract drift without a contract change.
  • Review text, URL, or key in a log, store, or fixture.
  • A new input path with no validation or size limit.
  • A user-facing claim stronger than the evidence.

Waits for another pull request

  • Formatting and import order a tool can decide.
  • A refactor that is not required by the issue.
  • Naming taste with no ambiguity for a reader.
  • An extra adapter or language that needs its own gate.
  • A dashboard or metric with no decision attached.

The right-hand list is not forbidden work; it is work that should not hold a tested change hostage. Write it as an issue and let the phase decide.

CHAPTER 11Demo and defense runbook

A demo is an evidence claim, not a performance. Show the honest states, the provenance, and one failure. A reviewer trusts a system that says “no estimate” more than one that never does.

11.4 Likely questions and answers

“Why not use a transformer?” The baseline meets the gate, runs on CPU, is deterministic, and gives stable linear attributions. A transformer is allowed only after it beats the baseline on the held-out sample, passes calibration and explanation stability, and ships as a new model version. Complexity is not evidence.

“Does 73 mean a 73% chance the review is fake?” No. It is 73% organic likelihood on the evaluation distribution, mapped to a score. The calibration is not Amazon prevalence, and the UI says it is an estimate from text patterns.

“Why postpone authentication?” The core value is the analysis path. Accounts are an access and persistence feature; building them first would delay the part the professor asked to see and add a database before its retention rules existed. Security is not postponed: validation, limits, CORS, secrets, and content-free logs exist from Phase 1.

“How do you know the adapter works?” A Phase 0 spike on three pre-chosen variants: at least five eligible reviews per page, at least 90% precision against a manual count, stable selectors across two loads. Fixtures lock the behaviour, and a selector miss produces an explicit unsupported state.

“What happens when Amazon changes the DOM?” The adapter stops matching and the extension reports unsupported. It does not scrape the page generically. The adapter is versioned, and a new selector set ships with new fixtures.

“How do you prevent overclaiming?” A normative bilingual copy deck, a forbidden-claim string test, signal summaries that describe influence rather than proof, and a model card that states limitations. The UI never says “fake,” “fraud,” “bot account,” or “verified.”

“What about privacy?” Review text is processed transiently, never logged or stored. Local history is opt-in metadata only. There is no external AI provider. The scoring service is internal and token-protected. Tests use a sentinel phrase to prove the text is absent from logs and storage.

“Is French supported?” Only if the French manual evaluation passes its own gate. The UI is translated regardless; UI translation does not imply model coverage. If the gate fails, French returns unknown.

“Why PostgreSQL in Phase 4?” Accounts and owned history need durable state. The analysis path still does not require a database. The schema stores metadata only, with retention, deletion, and no text column.

“How do you know the score and band agree?” One mapping function is used by training, evaluation, and serving; boundary tests cover every band edge and half-up rounding; the backend re-validates the band before returning it.

“What about LLM-generated or adversarial reviews?” It is a documented limitation. The model is trained on older public corpora and is not claimed to detect novel generated text. A new capability needs new data, a new gate, and a new model version.

“What would you do with more time?” More in-domain labels, a larger French sample, a transformer evaluated against the same gate, more adapters with fixtures, and hosted quotas. None of those is worth weakening the honest unknown state.

11.5 Preflight checklist

  • Scoring health 200 and the expected artifact hash.
  • Backend health 200 and /api/v1/version matches.
  • Extension loaded from the intended build; CORS origin matches.
  • Supported fixture/page open; three review types available: scored, low, unknown.
  • History cleared and off at the start, so opt-in is visible.
  • No secret, token, or personal data on screen; terminal font readable.
