CHAPTER 02GitHub strategy from zero

No repositories exist yet, which is an advantage: the operating model can be set correctly once. This chapter creates the repository, the rules, the board, and the automation before the first feature. It assumes a small course team, a private repository, and a single deliverable that a professor must be able to inspect.

Outcome of this chapter

One private monorepo, a protected main, a project board mapped to phases, four CI checks that run on every pull request, a release convention, and a security baseline. Every later chapter assumes this exists.

2.1 Decide the account and the visibility

DecisionRecommendationWhy

Academic integrity check

Confirm with the professor whether the repository may be public, whether the course platform requires a specific repository name, and whether a personal account is mandatory. Record the answer as an evidence line in docs/evidence/phase-0.md. Do not discover this at submission time.

2.2 One repository or several

Recommendation: one monorepo named trustloop. It contains three independently runnable components (backend/, scoring-service/, extension/), the shared contracts/v1/, the baseline docs/, and the operational files. This is already decision D07. The reasons are practical, not ideological:

BenefitWhat it buys the project
Atomic contract changesA schema change, the Java DTO change, the Python response change, and the extension rendering change can land in one pull request. With separate repositories, the contract is briefly broken across three histories.
One source of truthOne issue tracker, one board, one milestone per phase, one CI badge, one README a reviewer can follow.
Cheap cross-component testsThe contract workflow can check out all three components and run fixture tests together without publishing private packages.
Simple course submissionOne link, one release tag, one evidence folder. The report and the code cannot drift into different repositories.
Independent runtimes still preservedEach component keeps its own build file, tests, and runtime. The monorepo is a source-control decision, not a deployment decision.

When a split is justified

A split is justified only if a component needs an independent release cadence, a different access policy, or a build that cannot tolerate the others. For this project, none of those is true during Phases 0–5. If the professor nevertheless requires separate repositories, use four repositories, never three:

RepositoryContentsRelease unit
trustloop-contractsJSON schemas, examples, fixtures, contract README.contract-v1.0.0 tag
trustloop-backendSpring Boot API.v0.x.y tag
trustloop-scoringPython service, training, artifacts, model card.model-tl-text-x.y.z plus service tag
trustloop-extensionManifest V3 extension and adapters.v0.x.y tag

If you split, consume the contract repository as a pinned Git submodule at contracts/, and pin a tag, not a branch. A submodule on main gives you the worst of both worlds: separate histories and silent drift. The contract repository becomes the first thing released in every phase.

Do not split into three

Without a shared contract repository, the schema will be copied into each component and will diverge. The first symptom is one component accepting a reason code that another rejects. That is risk R-12, and it is entirely self-inflicted.

Binary policy

Do not commit restricted datasets, reviewer-level data, or large model binaries. Commit the dataset-manifest.json, metrics.json, and model card; publish the artifact bundle as a GitHub Release asset with a SHA-256 checksum. If a small model must be committed for the demo, keep it under roughly 5 MB and document why. Prefer release assets over Git LFS for a course project; LFS adds a dependency every teammate must install.

2.5 Branch and merge model

Use GitHub Flow: a protected main, short-lived branches, pull requests, squash merges, and tags for releases. Do not create a permanent develop branch. Do not create a branch per phase; phases are milestones and tags, not long-lived code lines.

BranchPatternUse
TrunkmainAlways green, always demoable. Protected. No direct pushes.
Featurefeat/api-analyze-endpointOne coherent change, linked to one issue.
Fixfix/extension-dedup-scrollA defect with a reproducible test.
Contractcontract/v1-reason-codesA contract change. Requires all three code owners.
Modelmodel/calibration-plattTraining, evaluation, or artifact changes. Includes metrics evidence.
Docsdocs/phase-1-evidenceDocumentation and evidence only.
Chorechore/ci-cacheTooling, dependencies, CI, repository housekeeping.

Branch rules. One branch, one purpose. Rebase on main before requesting review; do not merge main into the branch repeatedly. Target fewer than 400 changed lines and fewer than three days of life. If a change cannot fit, split it by seam — contract first, then consumer — rather than by file count. Delete the branch after merge.

Merge method

Enable squash merge only and disable merge commits and rebase merging. The pull-request title becomes the commit subject. This keeps a readable linear history and makes git bisect useful when the model or contract breaks.

2.6 Commit and pull-request conventions

Use Conventional Commits with a component scope. The format is type(scope): imperative summary, under 72 characters, with a body that explains why when the change is not obvious.

TypeWhenExample
featA user-visible or contract-visible capability.feat(api): add analyze endpoint with batch validation
fixA defect with a test that would have caught it.fix(extension): keep dedup keys stable across rescans
testTests only, no production behaviour.test(scoring): cover version mismatch on score response
docsDocumentation, decisions, evidence.docs: record Phase 0 spike result and fallback
refactorNo behaviour change.refactor(api): extract response validator from service
perfMeasured performance change.perf(scoring): batch vectorize ten reviews
ciWorkflows, caching, release automation.ci: add contract fixture workflow
choreDependencies, housekeeping, no product change.chore: bump Spring Boot patch version

Scopes: api, scoring, extension, contract, model, docs, ci. A commit that touches more than two scopes is usually two commits or a contract change that needs its own PR.

Pull-request template

Markdown · .github/PULL_REQUEST_TEMPLATE.md
## What
<one paragraph>
## Why
Closes #<issue>. <the user or system problem>
## Contract impact
- [ ] No change to contracts/v1
- [ ] Contract change: <schema/field/constant> + all consumers updated
## Privacy impact
- [ ] No new data collected, logged, or stored
- [ ] Reviewed: <what changed>
## Evidence
- [ ] Tests added/updated and passing
- [ ] Screenshots or recording for UI changes
- [ ] Metrics/model card update for model changes
## Risk
<new risk, changed risk, or "none">

Review rules. One approval is required for ordinary changes; two approvals, including every code owner, for contracts/, authentication, security configuration, and model gate changes. The author does not merge their own PR without a review. Review within one working day. A review comment is either a request for change or a question; avoid “nit” comments that block a merge on style when a formatter can decide.

Pull-request size and drafting

  • Open a draft PR as soon as the approach is visible; it is cheaper to redirect early.
  • Keep generated files, lockfiles, and fixtures in separate commits so the review focuses on logic.
  • If a PR needs a contract change, land the contract PR first and rebase the consumers onto it. Do not merge a consumer against an unreleased schema.
  • UI changes include a before/after screenshot and a keyboard/focus note. Model changes include the metric delta and the gate result.

Project board

Create one GitHub Project linked to the repository. Keep the default Status field and add: Phase (single select), Area (single select), Priority (single select), Size (XS–L), Risk (text or single select), and Owner (person). Use three views:

  • Current phase — filter phase = current, group by status, hide done.
  • My work — filter assignee = @me, sort by priority.
  • Risks and decisions — filter label:risk:* or type:decision, sorted by due date.

Enable the built-in workflows: item added → Backlog; pull request linked → In review; pull request merged → Done. Do not automate “In progress” from branch creation; it creates noise when branches are abandoned.

2.9 Branch protection and rulesets

Use a repository ruleset rather than classic branch protection; it is easier to audit and can target tags as well.

  1. Push the CI workflows first and open a throwaway PR so GitHub registers the check names.
  2. Go to Settings → Rules → Rulesets → New branch ruleset. Target main.
  3. Enable: require a pull request before merging; required approvals 1 (2 for a stricter team); dismiss stale approvals on new commits; require review from code owners; require conversation resolution; require linear history; block force pushes; block deletions; require branches to be up to date before merging.
  4. Require the status checks: backend / verify, scoring / test, extension / test, contract / validate, and docs / links if you add it.
  5. Add a second ruleset for tags matching v* and model-*: block deletion and non-fast-forward updates. Releases are immutable.
  6. Bypass list: empty, or the project lead only for an emergency. An emergency bypass is recorded in the phase evidence and followed by a retrospective issue.
Check-name trap

A required check that never runs blocks every PR forever. If you rename a workflow or job, update the ruleset in the same PR. Keep job names stable: verify, test, validate.

Signed commits are optional for a course project. If the team enables them, do it at kickoff for everyone; enabling halfway creates a history where half the commits are unverified and the rule becomes noise.

2.10 CI blueprint

Five workflows, each with path filters so a documentation commit does not run the Java build. All workflows use least-privilege permissions and cancel superseded runs.

Backend workflow — concrete shape

YAML · .github/workflows/backend.yml
name: backend
on:
  pull_request:
    paths: ["backend/**", "contracts/**", ".github/workflows/backend.yml"]
  push:
    branches: [main]
    paths: ["backend/**", "contracts/**"]
permissions:
  contents: read
concurrency:
  group: backend-${{ github.ref }}
  cancel-in-progress: true
jobs:
  verify:
    runs-on: ubuntu-latest
    timeout-minutes: 15
    env:
      TRUSTLOOP_CONTRACT_DIR: ${{ github.workspace }}/contracts/v1
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-java@v4
        with:
          distribution: temurin
          java-version: "21"
          cache: maven
      - name: Verify
        working-directory: backend
        run: mvn -B -ntp verify
      - name: Upload test reports
        if: always()
        uses: actions/upload-artifact@v4
        with:
          name: backend-test-reports
          path: backend/target/surefire-reports/
          retention-days: 14
Contract fixtures in CI

Pass the repository-level contract path through one environment variable, TRUSTLOOP_CONTRACT_DIR. Each component's test bootstrap reads it and falls back to ../contracts/v1 for local runs. Never copy fixtures into a component; copies drift.

What CI must not do

  • Do not download restricted datasets or train the full model in GitHub Actions. Data licensing, runner minutes, and reproducibility all suffer. Train locally or on a controlled machine; commit the metrics and publish the artifact as a release asset.
  • Do not use pull_request_target to run code from a fork. It grants secrets to untrusted code.
  • Do not echo environment variables, tokens, or request bodies. GitHub masks known secrets, but a transformed value can still leak.
  • Do not require a check that only runs on main; it will never appear on pull requests.

Nightly and manual workflows

  • Nightly contract check at 02:00 UTC: re-run the contract workflow against main and open an issue on failure. This catches schema drift after a merge.
  • Manual model gate (workflow_dispatch): run only when the artifact is available as a release asset; verify its SHA-256, load it, run the held-out metrics, compare against metrics.json, and fail on mismatch. It does not retrain.
  • Dependency review on pull requests that change lockfiles; block critical vulnerabilities with no fix.

2.12 Releases and versioning

Four version axes exist. Do not collapse them into one number.

AxisFormatRule
ApplicationvMAJOR.MINOR.PATCHSemVer for the repository release. A phase demo is a minor; a defended baseline is v1.0.0; an access-model change is a major.
Contractv1 directory, contract-v1.0.0 tagA breaking change creates contracts/v2/ and updates all consumers. Never edit v1 after freeze except to fix a documentation typo that does not change validation.
Modeltl-text-x.y.zMajor: label, score meaning, or band mapping. Minor: data, features, calibration, retraining. Patch: explanation copy or performance with no score change.
Adapteramazon.reviews.v1Breaking selector or extraction change increments the adapter version; the old adapter remains until retired.

Release procedure

  1. Confirm main is green and the phase evidence file is complete.
  2. Update versions in the build files, README status, and model card. Commit as chore(release): prepare vX.Y.Z.
  3. Create an annotated tag: git tag -a v1.0.0 -m "TrustLoop MVP v1.0.0". Push the tag.
  4. Create a GitHub Release from the tag. Attach: backend JAR, extension ZIP, model bundle (if not restricted), metrics.json, SHA256SUMS.
  5. Write release notes grouped as Added, Changed, Fixed, Known limitations. State the model version and the supported languages explicitly.
  6. Never move or re-create a published tag. A mistake gets a new patch version.
Phase tags

Also tag phase gates: phase-0-complete, phase-1-complete, and so on. They are not releases; they are checkpoints the report can cite. Link each tag in the phase evidence file.

2.14 Team cadence

A five-person team can map roles to components, but every role includes review and testing. Adjust if the team is smaller; do not leave a component without an owner.

RoleOwnsAlso responsible for
Project leadRepository, decisions, phase gates, integration.Contract review, risk register, demo script.
Backend leadSpring API, validation, scoring client, logs.Security baseline, contract DTOs, backend tests.
ML leadData, model, calibration, gate, explainer, artifact.Model card, evaluation report, reproducibility.
Extension leadAdapter, scanner, badge, panel, history.Accessibility baseline, adapter fixtures, i18n strings.
QA and docs leadTest plan, evidence, report, design assets.Cross-component contract tests, accessibility audit, copy review.

Weekly rhythm. Monday: 30-minute planning, choose issues for the week, confirm the gate target. Wednesday: 20-minute integration check, run the end-to-end path, surface blockers. Friday: 30-minute demo and gate review, tag if the gate passes. Keep decisions in the register, not in chat. Chat is for coordination; the repository is the record.

Work in progress. Limit each person to two active issues. A PR waiting for review counts as active. If a review is blocked for more than a day, the reviewer hands it to another code owner rather than letting it rot.

Pre-defense freeze

Stop feature merges 48 hours before the defense. Only fix/ branches with a failing test are allowed. The freeze protects the demo from a last-minute dependency update or a half-merged contract change.
