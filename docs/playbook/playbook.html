Examples assume Java 21 LTS, Spring Boot 3.x, Node 22 LTS, and Python 3.12, because those versions have the widest library and tooling support. Your course may mandate different versions. Working method

How to use this book

Read the whole book once before writing code. Then work one phase at a time, one step at a time, and do not start the next phase until the gate evidence exists.

Four conventions

1. Steps are ordered, not optional

Each step lists its dependencies. If a dependency is missing, fix that first. Parallel work is allowed only where the dependency graph says it is.

2. Every step ends with proof

A step is done when the verification block passes and the evidence is recorded. “It worked on my machine” is not evidence; a test, a log excerpt, a metrics file, or a signed checklist is.

3. The contract is the integration point

Components do not integrate through conversation. They integrate through contracts/v1/ fixtures. Change the contract first, in its own pull request, with all three consumers updated.

4. Honesty beats completeness

When a model, language, adapter, or page is not validated, the product says so. An explicit unknown is a feature. A fabricated score is a defect.

What “done” means at a gate

A phase gate is not a meeting where someone says “looks good.” It is a short review with five questions:

  1. Does the phase exit condition in the delivery plan hold, with evidence?
  2. Are the tests for this phase present, green, and run in CI?
  3. Did any decision change? Is the decision register updated?
  4. Did any risk change likelihood or impact? Is the risk register updated?
  5. Can a person who did not write the code run the demo from the runbook?
The one rule that saves the project

Never trade a test or an honest unknown for a prettier demo. Cut adapters, admin polish, or deployment instead. The score’s meaning is the product.

CHAPTER 01The system in one page

Before the steps, hold the whole shape in your head. TrustLoop is three processes and one contract. The contract is the product boundary; everything else is an implementation detail.

1.1 What TrustLoop does

TrustLoop is a browser extension with a Spring Boot API and a Python scoring service. On a supported product-review page, it identifies review cards, extracts the review text, and sends up to ten reviews per request to the API. The API validates the request, calls the scoring service, validates the result, and returns one result per review. The extension renders a badge beside each review and an explanation panel on demand.

The model estimates p_organic: the probability that the review text is organic rather than manipulated, based only on text patterns and a transient within-batch duplicate flag. That probability is calibrated to the evaluation distribution, then mapped to an integer score and one of six fixed bands. It is an estimate about text, not a statement about the reviewer or the product.

The sentence to memorize

“TrustLoop estimates whether review text looks organic or manipulated, shows its evidence quality, and explains which text patterns influenced the estimate. It does not verify purchases, identify people, prove fraud, or rate products.”

1.2 What it refuses to do

RefusalWhy it matters
Verify a purchase or reviewer identityModel v1 never receives reviewer names, profiles, ratings, or verified-purchase flags. Claiming verification would be false.
Prove a review is fake or trueLabels are noisy proxies for text patterns. The UI says “signals,” never “proof.”
Score a product or a pageAveraging review scores hides mixed evidence and invents a meaning the score does not have. No page aggregate exists.
Scrape arbitrary page textOnly eligible review cards inside a supported adapter container are extracted. A selector miss is an explicit unsupported state.
Fall back to a heuristic scoreIf the model is unavailable or a language fails its gate, the result is UNKNOWN; validated descriptive patterns may produce SIGNALS_ONLY with no score.
Send live review text to an external AI providerInference is local or private. Review text is processed transiently and never logged or persisted.
Silently mix engines or model versionsEvery result carries provenance. A version mismatch invalidates the batch rather than hiding the mismatch.

1.7 Non-negotiables

Honesty

No unvalidated score. No fabricated 0 or 50. No “bot” or “fraud” claim from a band. No page aggregate. Low evidence stays visible and qualified.

Privacy

No request or response body logging. No raw text in local history. No URLs, review keys, reviewer identifiers, or persistent fingerprints. No external AI provider for live text.

Testability

Tests arrive with the behaviour. Contract fixtures are shared, not re-created per component. The model gate is a script, not a slide.

Operability

The local admin surface is loopback-only and absent by default. The scoring service is internal-only. Every request is traceable by ID, and logs stay content-free.

Scope discipline

Breadth is optional; meaning is not. If time runs short, cut a second adapter, admin polish, or deployment. Never cut the gate, the tests, or the honest unknown state.

2.2 One repository or several

Recommendation: one monorepo named trustloop. It contains three independently runnable components (backend/, scoring-service/, extension/), the shared contracts/v1/, the baseline docs/, and the operational files. This is already decision D07. The reasons are practical, not ideological:

BenefitWhat it buys the project
Atomic contract changesA schema change, the Java DTO change, the Python response change, and the extension rendering change can land in one pull request. With separate repositories, the contract is briefly broken across three histories.
One source of truthOne issue tracker, one board, one milestone per phase, one CI badge, one README a reviewer can follow.
Cheap cross-component testsThe contract workflow can check out all three components and run fixture tests together without publishing private packages.
Simple course submissionOne link, one release tag, one evidence folder. The report and the code cannot drift into different repositories.
Independent runtimes still preservedEach component keeps its own build file, tests, and runtime. The monorepo is a source-control decision, not a deployment decision.

When a split is justified

A split is justified only if a component needs an independent release cadence, a different access policy, or a build that cannot tolerate the others. For this project, none of those is true during Phases 0–5. If the professor nevertheless requires separate repositories, use four repositories, never three:

RepositoryContentsRelease unit
trustloop-contractsJSON schemas, examples, fixtures, contract README.contract-v1.0.0 tag
trustloop-backendSpring Boot API.v0.x.y tag
trustloop-scoringPython service, training, artifacts, model card.model-tl-text-x.y.z plus service tag
trustloop-extensionManifest V3 extension and adapters.v0.x.y tag

If you split, consume the contract repository as a pinned Git submodule at contracts/, and pin a tag, not a branch. A submodule on main gives you the worst of both worlds: separate histories and silent drift. The contract repository becomes the first thing released in every phase.

Do not split into three

Without a shared contract repository, the schema will be copied into each component and will diverge. The first symptom is one component accepting a reason code that another rejects. That is risk R-12, and it is entirely self-inflicted.

2.5 Branch and merge model

Use GitHub Flow: a protected main, short-lived branches, pull requests, squash merges, and tags for releases. Do not create a permanent develop branch. Do not create a branch per phase; phases are milestones and tags, not long-lived code lines.

Fixfix/extension-dedup-scrollA defect with a reproducible test.

Branch rules. One branch, one purpose. Rebase on main before requesting review; do not merge main into the branch repeatedly. Target fewer than 400 changed lines and fewer than three days of life. If a change cannot fit, split it by seam — contract first, then consumer — rather than by file count. Delete the branch after merge.

Merge method

Enable squash merge only and disable merge commits and rebase merging. The pull-request title becomes the commit subject. This keeps a readable linear history and makes git bisect useful when the model or contract breaks.

Review rules. One approval is required for ordinary changes; two approvals, including every code owner, for contracts/, authentication, security configuration, and model gate changes. The author does not merge their own PR without a review. Review within one working day. A review comment is either a request for change or a question; avoid “nit” comments that block a merge on style when a formatter can decide.

Pull-request size and drafting

  • Open a draft PR as soon as the approach is visible; it is cheaper to redirect early.
  • Keep generated files, lockfiles, and fixtures in separate commits so the review focuses on logic.
  • If a PR needs a contract change, land the contract PR first and rebase the consumers onto it. Do not merge a consumer against an unreleased schema.
  • UI changes include a before/after screenshot and a keyboard/focus note. Model changes include the metric delta and the gate result.

2.9 Branch protection and rulesets

Use a repository ruleset rather than classic branch protection; it is easier to audit and can target tags as well.

  1. Push the CI workflows first and open a throwaway PR so GitHub registers the check names.
  2. Go to Settings → Rules → Rulesets → New branch ruleset. Target main.
  3. Enable: require a pull request before merging; required approvals 1 (2 for a stricter team); dismiss stale approvals on new commits; require review from code owners; require conversation resolution; require linear history; block force pushes; block deletions; require branches to be up to date before merging.
  4. Require the status checks: backend / verify, scoring / test, extension / test, contract / validate, and docs / links if you add it.
  5. Add a second ruleset for tags matching v* and model-*: block deletion and non-fast-forward updates. Releases are immutable.
  6. Bypass list: empty, or the project lead only for an emergency. An emergency bypass is recorded in the phase evidence and followed by a retrospective issue.
Check-name trap

A required check that never runs blocks every PR forever. If you rename a workflow or job, update the ruleset in the same PR. Keep job names stable: verify, test, validate.

Signed commits are optional for a course project. If the team enables them, do it at kickoff for everyone; enabling halfway creates a history where half the commits are unverified and the rule becomes noise.

Contract fixtures in CI

Pass the repository-level contract path through one environment variable, TRUSTLOOP_CONTRACT_DIR. Each component's test bootstrap reads it and falls back to ../contracts/v1 for local runs. Never copy fixtures into a component; copies drift.

What CI must not do

  • Do not download restricted datasets or train the full model in GitHub Actions. Data licensing, runner minutes, and reproducibility all suffer. Train locally or on a controlled machine; commit the metrics and publish the artifact as a release asset.
  • Do not use pull_request_target to run code from a fork. It grants secrets to untrusted code.
  • Do not echo environment variables, tokens, or request bodies. GitHub masks known secrets, but a transformed value can still leak.
  • Do not require a check that only runs on main; it will never appear on pull requests.

Nightly and manual workflows

  • Nightly contract check at 02:00 UTC: re-run the contract workflow against main and open an issue on failure. This catches schema drift after a merge.
  • Manual model gate (workflow_dispatch): run only when the artifact is available as a release asset; verify its SHA-256, load it, run the held-out metrics, compare against metrics.json, and fail on mismatch. It does not retrain.
  • Dependency review on pull requests that change lockfiles; block critical vulnerabilities with no fix.

Request ID rules

Accept 1–64 characters matching [A-Za-z0-9-]. If absent or malformed, generate a UUIDv4. Set the response header even on errors. Put the ID in the logging context and remove it in a finally block so a reused thread never leaks another request’s ID.

Java · request ID filter, essential lines
String id = request.getHeader("X-Request-Id");
if (id == null || !id.matches("[A-Za-z0-9-]{1,64}")) {
    id = UUID.randomUUID().toString();
}
MDC.put("requestId", id);
response.setHeader("X-Request-Id", id);
try {
    chain.doFilter(request, response);
} finally {
    MDC.remove("requestId");
}

Size rules

  • Check Content-Length when present; reject immediately if it exceeds 131,072 bytes.
  • For chunked requests, wrap the input stream with a counting limiter and abort once the limit is crossed. A header check alone is not enough.
  • Also cap the JSON parser’s nesting depth and string length; a deeply nested body can exhaust memory even under the byte limit.
  • Return 413 with the error envelope, not a container-generated HTML error page.

Rate rules

  • Use an in-memory token bucket per client IP. The local default is 60 requests per minute. Bucket4j is a reasonable choice; a small ConcurrentHashMap implementation is acceptable if tested.
  • Do not trust X-Forwarded-For unless the backend is behind a known proxy and configured to read it. Otherwise a client can spoof the key.
  • Exclude nothing from the limit in production; health checks are local and cheap. In the performance test, raise the test-profile limit explicitly rather than special-casing an endpoint.
  • Emit Retry-After in seconds and keep the message generic: "Request rejected".

CORS rules

  • Allow only the configured extension origin(s), POST and GET, and the headers Content-Type and X-Request-Id.
  • Expose X-Request-Id and Retry-After so the extension can show and retry correctly.
  • Do not enable credentials in the MVP; there are no cookies. When authentication arrives in Phase 4, revisit this decision explicitly.
  • Pin the packed extension ID for any shared environment. A wildcard chrome-extension://* pattern is a development-only convenience and must be impossible to enable in production.

5.5 Build the data pipeline

STEP 1.6

Acquire, normalize, deduplicate, and split

Owner ML lead  |  Time 4–6 days  |  Depends D22; licensed data

Goal. A reproducible, leakage-free dataset with a manifest, stable splits, and no live review text.

Pipeline stages

  1. Acquire. Download each licensed source into data/raw/<source>/ using a script, never by hand. Record the URL, access date, license, and SHA-256 in the manifest.
  2. Normalize. Apply Unicode NFKC; strip HTML tags; remove zero-width and control characters except newline/tab; collapse whitespace; keep punctuation and case for the feature pipeline. Compute the word count after normalization, using the same definition as the service.
  3. Map labels. Convert each source’s label to organic/manipulated using an explicit table. Mark uncertain or unlabelable items and exclude them from training and from the primary metric. Never merge a reviewer-level flag into a review-level label without documentation.
  4. Filter. Drop training items below 20 words to match deployment; record how many were dropped. Do not silently keep them and then evaluate only on long reviews.
  5. Deduplicate. Use MinHash with five-word shingles at a 0.80 similarity threshold, or cosine similarity on normalized text for a smaller corpus. Remove near-duplicates across the entire corpus before splitting.
  6. Split by group. Group by product or source item, never by individual review. Assign groups to train/dev/calibration/test so no group appears in two splits. Verify the split with an assertion, not a visual scan.
  7. Balance report. Record class counts per split, per source, and per language. Do not resample unless the method and its effect are documented.
  8. Freeze. Write split-manifest.json with group IDs, item counts, seeds, and hashes. Training reads the manifest; it does not re-split on every run.

Baseline

Python · baseline shape

Training protocol

  1. Tune only on dev: C, min_df, and feature caps. Keep the grid small; a large grid on a small corpus overfits the dev split and wastes the schedule.
  2. Use class weights rather than duplicating the minority class. If resampling is used, document it and apply it to training only.
  3. Fit calibration on the dedicated calibration split: Platt scaling for small samples, isotonic only when the split is large enough to support it. Choose the method by dev reliability, then report on test.
  4. Set random seeds and single-threaded BLAS for deterministic outputs (OMP_NUM_THREADS=1, OPENBLAS_NUM_THREADS=1). Record the environment.
  5. Touch the test split once per candidate. Report the result even when it is disappointing; do not keep tuning until it passes.

Score mapping, implemented once

Put the score and band functions in one module used by training, evaluation, and serving. Unit-test every boundary and a half-up case such as p_organic = 0.705 → 71.

5.7 Build the explanation

STEP 1.9

Attribute the linear model and aggregate signals

Owner ML lead  |  Time 2–3 days  |  Depends 1.7

Goal. At most five stable, human-readable signals with direction, optional validated contribution, and no quoted review text.

Method

  • For the linear baseline, a feature’s contribution is its coefficient for the predicted class multiplied by its normalized value. Negative values push toward manipulated; positive values push toward organic, depending on the class encoding. Document the sign convention once.
  • Aggregate token features into the named signal groups in Appendix E. Some groups are model features; others are rule-based observations (for example, within-batch duplication) and may be qualitative.
  • Normalize signed contributions across the full feature set so the total absolute contribution is 1. Return the top five with their original normalized values. Do not renormalize the returned subset; that would make a weak signal look strong.
  • If a signal cannot be attributed stably, omit its numeric contribution and return the qualitative summary. The contract allows this; the UI must handle it.
  • Never quote the review text, a name, a URL, or a personal detail in a signal summary. Summaries are fixed templates from the copy deck.

STEP 1.11

Goal. The extension extracts only eligible review text from the supported adapter, once per review per page session, in batches of at most ten.

Adapter interface

JavaScript · adapter shape
export const amazonReviewsV1 = {
  id: "amazon.reviews.v1",

Eligibility

JavaScript · eligibility check, essential lines
export function isEligible(card) {
  const style = getComputedStyle(card);
  if (style.display === "none" || style.visibility === "hidden") return false;
  if (card.closest("[aria-hidden='true']")) return false;
  const rect = card.getBoundingClientRect();
  if (rect.width === 0 || rect.height === 0) return false;
  return normalizeText(extractText(card)).length > 0;
}

Viewport intersection only schedules work; it does not decide eligibility. Two users scanning the same DOM state must see the same review set regardless of scroll position. This prevents the score set from depending on how far someone happened to scroll.

Deduplication

  • Use the adapter-provided stable card ID when present. Map it to a random, opaque reviewKey held in memory for the page session.
  • When no stable ID exists, hash the normalized text with a per-session random salt. The hash and the salt never leave memory.
  • Use the DOM ordinal only as a tie-breaker, never as the primary key; virtualized lists reuse nodes and reorder them.
  • Discard the map on navigation. Never write a key, a hash, or a salt to local history, storage, or a server.
  • Track submitted keys in a set so scrolling and mutation do not resubmit the same review. A manual retry for an unavailable batch may resubmit, but an automatic loop may not.

Scanning loop

  • Debounce DOM mutations by 750 ms. Enforce a minimum interval of 2,000 ms between scans to avoid a mutation storm.
  • Observe the adapter’s container, not the whole document. Disconnect the observer on navigation and reinitialize on the new page.
  • Use an IntersectionObserver to prioritize visible cards, but build the eligible set from the DOM, not from the viewport.
  • Batch up to 10 unscored eligible reviews. Send batches sequentially; do not fire ten parallel requests.
  • Abort an in-flight request on navigation. The service worker enforces a 6-second ceiling with AbortController; the backend ceiling is 4 seconds.
Verify
  • A hidden review is excluded; a visible review is included; a zero-size card is excluded.
  • Scrolling does not resubmit a review; a DOM mutation does not resubmit an already-submitted key.
  • A batch never exceeds 10, even when 25 reviews are eligible.
  • The dedup map is empty after navigation, and no key or hash exists in storage.
  • An unsupported layout yields UNSUPPORTED_PAGE, never a generic scrape.

CHAPTER 08 · PHASE 4Accounts, ownership, and persistence

Authentication is deliberately last because it is an access feature, not a prerequisite for scoring. When it arrives, it brings the first database and the first durable user data. The rule that protects the project is simple: accounts may own metadata about a scan, but never the review text, the review key, or a persistent fingerprint.

Phase exit condition

The access matrix is verified by tests. Admin functions require an authenticated admin role. History ownership and retention are enforced. No raw review text is stored. Migrations reproduce from an empty database. Tokens, passwords, and deletion behave as documented.

8.1 Decide the scope before writing a schema

Do not start with tables. Start with the answers a schema must encode. Write them into a decision row and into the phase evidence; a schema without a retention rule is a liability.

Who owns a history rowExactly one user. Every read, delete, and export filters by the authenticated user ID.
RetentionDefine a maximum (for example 180 days) and enforce a scheduled purge. The user can clear earlier. Local history remains 30 days/100 entries.

STEP 4.2

Registration, login, refresh, logout, and the access matrix

Owner Backend lead  |  Time 5–7 days  |  Depends 4.1; contract decision

Goal. Passwords stored safely, tokens short-lived and revocable, roles enforced at the route level, and no account enumeration through error messages.

Password and token rules

  • Hash passwords with Argon2id via Spring Security’s encoder. If the native dependency is unavailable on the course environment, use BCrypt with cost 12 and document the choice. Never store or log the plaintext.
  • Access token: signed JWT, 15-minute lifetime, subject = user ID, role claim, issuer and audience set. Do not put email, name, or any review data in the token.
  • Refresh token: 256-bit random value, stored only as a hash, 30-day lifetime, rotated on every use. Reuse of an old token revokes the family.
  • Signing key from the environment, at least 256 bits. Never commit it. Rotate with a key ID so old tokens can be validated during a short overlap.
  • Login rate limit stricter than the general API limit (for example 5 attempts per minute per IP and per account), with a generic error message and a constant-time-ish path that does not reveal whether the account exists.
  • Logout revokes the refresh token. Client-side token deletion alone is not logout.

Extension token storage

  • Keep the access token in memory in the service worker. Keep the refresh token in chrome.storage.local only if refresh is implemented; never sync it.
  • Do not put tokens in content scripts, DOM attributes, URLs, or logs. Content scripts request an analysis through the worker.
  • On logout or account deletion, clear every token and every history entry.
  • If the extension is ever published to a store, review the privacy policy and host-permission justification. For the course, an unpacked build is sufficient.
401, 403, and 404 mean different things

401: no valid authentication. 403: authenticated but not allowed. 404: the resource does not exist or is not visible to this user. Do not return 404 for a documented admin route to “hide” it; that makes debugging impossible and does not add security. Do return 404 for another user’s history row to avoid confirming its existence.

Verify
  • A password hash is present in the database and the plaintext is absent from logs and responses.
  • An access token expires; an expired token returns 401; a refresh rotates and the old refresh token is rejected.
  • A USER calling an admin route gets 403; an unauthenticated caller gets 401.
  • User A cannot read, delete, or infer User B’s history; the response is 404 or an empty scoped list, never B’s data.
  • Login failures are rate-limited and use a generic message.
  • No token appears in a URL, a log, or a response body other than the token endpoint.

8.4 Implement history ownership and retention

STEP 4.3

Ownership filters, purge job, and deletion

Owner Backend lead  |  Time 2–3 days  |  Depends 4.2

Goal. Every history row is owned, every read is scoped, and old data disappears on schedule without a manual cleanup.

Rules

  • Never accept a userId from the client. Derive it from the authenticated principal.
  • Write history only after a result is returned, and only if the user has enabled server history. The analysis path must work with history disabled.
  • Store the same metadata as local history: timestamp, hostname, adapter ID, status, score/verdict when scored, evidence, engine, model version, reason code. No text, key, URL, IP, or user agent.
  • Purge rows older than the retention limit with a scheduled job. Log only the count and duration, never a row’s content.
  • Account deletion cascades history and refresh tokens. Audit entries keep an actor ID according to the audit policy, or are anonymized; decide and test.
  • Pagination is required. An unbounded history query is a denial-of-service vector and a privacy exposure.
Verify
  • Two users with history see only their own rows, including after pagination.
  • A history row cannot be created with a score and status UNKNOWN, or with no owner.
  • The purge job removes only expired rows and reports a count.
  • Deleting an account removes its history and refresh tokens.
  • The database contains no review text, key, URL, or fingerprint column.

10.9 The five-minute self-review

Do this before you request review. It is cheaper than a review cycle and it catches the failures reviewers should not have to find.

  1. Re-read the issue’s acceptance checks and map each one to a test or a manual step.
  2. Run the new test without the fix, then with it. If the result does not change, the test proves nothing.
  3. Read your own diff in the GitHub “Files changed” view, not in the editor. Editors hide omissions.
  4. Check the contract, privacy, and security boxes honestly; write one sentence for each where the answer is not obvious.
  5. Write the PR paragraph: what changed, why, what you verified, and what you did not.

Blocks the merge

  • A failing test or a gate that was not run.
  • Contract drift without a contract change.
  • Review text, URL, or key in a log, store, or fixture.
  • A new input path with no validation or size limit.
  • A user-facing claim stronger than the evidence.

Waits for another pull request

  • Formatting and import order a tool can decide.
  • A refactor that is not required by the issue.
  • Naming taste with no ambiguity for a reader.
  • An extra adapter or language that needs its own gate.
  • A dashboard or metric with no decision attached.

The right-hand list is not forbidden work; it is work that should not hold a tested change hostage. Write it as an issue and let the phase decide.

“Why not use a transformer?” The baseline meets the gate, runs on CPU, is deterministic, and gives stable linear attributions. A transformer is allowed only after it beats the baseline on the held-out sample, passes calibration and explanation stability, and ships as a new model version. Complexity is not evidence.

“Does 73 mean a 73% chance the review is fake?” No. It is 73% organic likelihood on the evaluation distribution, mapped to a score. The calibration is not Amazon prevalence, and the UI says it is an estimate from text patterns.

“Why postpone authentication?” The core value is the analysis path. Accounts are an access and persistence feature; building them first would delay the part the professor asked to see and add a database before its retention rules existed. Security is not postponed: validation, limits, CORS, secrets, and content-free logs exist from Phase 1.

“How do you know the adapter works?” A Phase 0 spike on three pre-chosen variants: at least five eligible reviews per page, at least 90% precision against a manual count, stable selectors across two loads. Fixtures lock the behaviour, and a selector miss produces an explicit unsupported state.

“What happens when Amazon changes the DOM?” The adapter stops matching and the extension reports unsupported. It does not scrape the page generically. The adapter is versioned, and a new selector set ships with new fixtures.

“How do you prevent overclaiming?” A normative bilingual copy deck, a forbidden-claim string test, signal summaries that describe influence rather than proof, and a model card that states limitations. The UI never says “fake,” “fraud,” “bot account,” or “verified.”

“What about privacy?” Review text is processed transiently, never logged or stored. Local history is opt-in metadata only. There is no external AI provider. The scoring service is internal and token-protected. Tests use a sentinel phrase to prove the text is absent from logs and storage.

“Is French supported?” Only if the French manual evaluation passes its own gate. The UI is translated regardless; UI translation does not imply model coverage. If the gate fails, French returns unknown.

“Why PostgreSQL in Phase 4?” Accounts and owned history need durable state. The analysis path still does not require a database. The schema stores metadata only, with retention, deletion, and no text column.

“How do you know the score and band agree?” One mapping function is used by training, evaluation, and serving; boundary tests cover every band edge and half-up rounding; the backend re-validates the band before returning it.

“What about LLM-generated or adversarial reviews?” It is a documented limitation. The model is trained on older public corpora and is not claimed to detect novel generated text. A new capability needs new data, a new gate, and a new model version.

“What would you do with more time?” More in-domain labels, a larger French sample, a transformer evaluated against the same gate, more adapters with fixtures, and hosted quotas. None of those is worth weakening the honest unknown state.

Appendix E — Signal taxonomy

Seven named patterns. Direction is preserved; only the top five by absolute contribution are returned. A signal says that a pattern contributed to the model output — never that it proves deception, intent, or identity.

CodeEnglish summary templateDirectionDefinition and limits
REPEATED_PHRASINGRepeats the same phrasingManipulativeRepeated n-grams or sentence templates within one review. Repetition also occurs in authentic reviews.
CROSS_REVIEW_DUPLICATEShares wording with other visible reviewsManipulativeServer-derived batch duplicate flag. Only within the request (maximum 10 reviews), not the whole page. Shared wording can be a template or a translation.
GENERIC_WORDINGUses generic wording with few concrete detailsManipulativeLow specificity and high generic-lexicon density. Domain-dependent; not proof of intent.
PROMOTIONAL_TONEReads like promotional copyManipulativePromotional lexicon and call-to-action patterns. Advertising and deception are not the same thing.
EXTREME_CLAIMSMakes extreme or unverifiable claimsManipulativeSuperlatives and absolute assertions. Stylistic; many genuine reviews do this.
CONCRETE_DETAILIncludes a concrete usage detailOrganicSpecificity features such as use case, duration, comparison. Detail can be fabricated.
LEXICAL_VARIETYShows varied, natural wordingOrganicType-token ratio and related diversity features. Unstable on short texts; model-dependent, so not used in SIGNALS_ONLY.

Rules for rendering a signal

  • Never quote the review. No raw text, names, URLs, product identifiers, or personal details in a summary or a tooltip.
  • Direction stays visible. A manipulative signal and an organic signal must not look identical. Use label, icon, and text — not colour alone.
  • Contributions are conditional. Show a number only when the explainer passes the stability and determinism checks. Otherwise the signal is qualitative and carries no percentage.
  • The returned subset is not renormalized. Contributions are normalized across the full feature set, then the top five are shown with their original values.
  • SIGNALS_ONLY uses observable patterns only. Cross-review duplication and repeated phrasing may be served without a model. Lexical variety and any model-dependent attribution may not.

Parity checks worth writing once. Assert that the Java enum, the Python enum, and the TypeScript union contain exactly the same reason codes and verdict codes; assert that every fixture round-trips through all three DTOs; assert that a service response with a score on an UNKNOWN is rejected by the backend and by the extension. Do not train in CI

Training is a deliberate, recorded act with a fixed seed, a dataset manifest, and a model card. CI validates artifacts and interface shape. A pipeline that silently retrains produces a model nobody evaluated — and a model version that no longer matches the reported gate.
